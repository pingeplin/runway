# 2609.0003 Blueprint 5.x — Abandoned. Post-mortem

**Date:** 2026-09-10
**Status:** approved
**Author:** EP Lin
**Doc type:** ADR (record)

Blueprint 5.0, 5.1, and 5.1.1 are abandoned. The plugin on `main` stays
at 4.0.0. The FeatureBench harness fix that the work uncovered stays. The
5.x implementation is preserved in git history on `worktree-blueprint-slim`
(commits `2063a62` … `f020b96`) and is not to be merged.

This document records what was tried, what was observed, what did not
help, and the original ideas — so the next attempt starts from evidence
rather than from the same intuitions.

## The original ideas

Stated by EP before any design work, in order:

1. **Slim the plugin.** In three months on 4.0 the only path ever used
   was `/blueprint` followed by an external `/loop` re-running
   implement → verify until the referee's verdict was clean enough to
   hand to a human. `/refactor`, `/review`, `/test-conventions` were
   never invoked. `commit-writer` felt like a wasted agent.
2. **Build the loop in.** The referee loop paid off on complex tasks —
   on the most recent one the verdict found a blind spot the implementer
   had missed — so the per-round human gates were ceremony; the human's
   real job is the final review.
3. **Loop the documents too.** 4.0 specs came out with internal
   contradictions, sentences that did not say what they meant, and
   ordering that made the reader scroll. The same produce → judge →
   revise loop should polish design docs and specs.
4. **(After the 5.0 result)** The loop's job is only two things: fix
   internal contradictions, and find scope that is related to the goal
   but not yet covered. It should ask a human only when a change would
   alter product behaviour. An inferred decision that is goal-related
   and does not change overall behaviour should be included in the spec
   by default. Persist the evaluator's ledger so the loop's effect can
   be measured.

Ideas 1 and 2 were never tested by the benchmark: FeatureBench exercises
`/spec` and a single `/verify` round, not the implement loop. Idea 3 is
what 5.0 built. Idea 4 is what 5.1 built on top.

## What was built

- **5.0** (`2063a62`): four skills, two agents, one loop protocol
  (`references/loop.md`) with a fresh report-only `evaluator` each round,
  whole-artifact rewrite, a ledger owned by the calling skill, round cap
  3, stop rules READY → NEEDS-HUMAN → cap → stuck. Coherence phase added
  to both review methodologies. 16 files, 2,192 lines (from 24 / 3,392).
- **5.1** (`e6ecf86`): every finding typed `contradiction` /
  `uncovered` / `behavior-change`; scope rule "a judge may add scope,
  never remove it"; `uncovered` items added by the producer marked
  `[INFERRED]`; stop rules reordered so NEEDS-HUMAN fires only when no
  autonomous row is open; ledger persisted as `{artifact}.ledger.md`;
  harness stage 01 captures it.
- **5.1.1** (`f020b96`): the scope rule extended to name "known
  blocker", "environment blocker", "pre-existing gap", "do not attempt
  to fix" as the same fence.

## What was observed

All numbers are from the history-masked harness, five astropy tasks,
one seed, one day (`evals/blueprint-featurebench/reports/2609_clean_paired_astropy_n5/`).

| | A — no spec | 4.0 spec | 5.0 spec ⟲ | 5.1 spec ⟲ |
|---|---|---|---|---|
| Mean hidden-test pass rate | 0.42 | **0.84** | 0.37 | 0.70 |
| Resolved | 0/5 | 1/5 | 1/5 | 1/5 |
| Spec cost / task | — | $15.88 | $15.36 | $18.69 |
| Spec wall / task | — | 33 min | 52 min | 56 min |

**1. The oracle leaked through git history, and every number before
2026-09-10 is invalid.** Working-tree masking (2608) left the upstream
commit in the extracted testbed; the 4.0 specs literally told the agent
"recoverable via `git show HEAD:`". The published "0/5 → 3/5 resolved"
was partly the spec transcribing the answer. This was found only because
5.0's odd result (agent stopped writing tests) was chased to its cause.
Fixed in `_common.reinit_git` (`1910873`). The implementing agent was
never exposed (fb infer re-inits git in the container), so Arm A stands.

**2. The 5.0 loop made specs worse than no spec.** 0.42 → 0.37. The
mechanism was scope narrowing: the evaluator's scope-discipline phases
fenced each spec to the literal problem statement; the implementing
agent honoured the fence ("outside my stated scope … left untouched");
FeatureBench masks a whole feature including the helpers the hidden
tests reach. The 4.0 single-pass writer, uncorrected, kept its instinct
to "restore everything stripped from this file" — and that instinct is
worth 0.42 → 0.84.

**3. 5.1's fix recovered most of the loss, then hit the same fence under
a new name.** 0.37 → 0.70. `vo` went 0.00 → 1.00 exactly as the probe
predicted. `lombscargle` stayed at 0.03: its 5.1 spec wrote "Known
Environment Blockers — do not attempt to fix `get_err_str`". Forbidding
the words "out of scope" moved the fence to "environment blocker". 5.1.1
named that wording too. This is whack-a-mole against a producer that
will always find a new phrase for a boundary it wants to draw.

**4. The loop does not converge.** Every 5.1 spec hit the 3-round cap
still raising findings — 20 to 40 ledger rows per task, roughly two
`uncovered` per `contradiction`, with round 3 still adding 6–10 rows. A
fresh judge each round finds fresh things; the cap, not convergence,
ends the loop. Cost 1.2× and wall time 1.7× the 4.0 single pass.

**5. The thing 5.0 was built to fix was never measured.** No harness
stage captures spec coherence — contradictions, terminology drift,
ordering. The ledger (5.1) records what the judge *raised*; it does not
say whether the final document is more coherent than a 4.0 document.
The entire 5.x line optimised an unmeasured property and regressed a
measured one.

**6. Headless producers do not follow the ledger format.** Status
written as phrases, later rounds shrunk to four columns. The harness
was made tolerant; the protocol's precision was not respected by the
model that had to follow it.

**7. Environment cost was large and unrelated.** A podman machine
rebuilt as libkrun without Rosetta crashed the in-container Claude
binary at start-up; Rosetta is read at machine start, not init; a
`containers.conf` pin was needed. Two inference runs were lost to this
at ~$0 but hours of wall time. `~/.config/containers/containers.conf`
now carries `provider = "applehv"`, `rosetta = true`.

## Adjustments that did not help

- **Report-only evaluator + whole-document rewrite** (5.0). The premise
  — that in-place editing by the evaluator caused the incoherent 4.0
  specs — was never verified; the rewrite loop's output was not measured
  for coherence, and it narrowed scope as a side effect.
- **Coherence phase** in both methodologies. Unmeasured. Possibly
  contributed to narrowing (it rewards a tidy document, and tidy means
  smaller).
- **Kind taxonomy + scope rule** (5.1). Partial: 0.37 → 0.70 of a 0.84
  target. It fixes the case it was written from (`vo`) and misses the
  next phrasing (`lombscargle`).
- **Naming more fence phrases** (5.1.1). Not measured; by construction
  it cannot be complete.
- **NEEDS-HUMAN reordering.** Never exercised — no headless run produced
  a `behavior-change` question that stopped the loop.
- **Ledger persistence.** Useful as a diagnostic (it is how the
  non-convergence in §4 is known); no effect on outcomes.
- **Merging three evaluators into one, deleting five agents and three
  skills.** Harmless, but the slimming was never the problem and its
  benefit is maintenance, not quality.

## What is worth keeping

- The harness history-masking fix and the clean paired numbers. The
  4.0 spec's effect is real: +0.42 pass rate at ~$16/task.
- The diagnosis: on this benchmark, a spec's value is breadth —
  "restore everything stripped from the touched files" — and any review
  step that rewards a narrower, tidier document works against it.
- The ledger format as a diagnostic instrument, if a loop is ever tried
  again.
- The observation that the implement loop (idea 2) was never measured.
  FeatureBench Arm C is a one-round `/verify`; the loop EP actually uses
  has no benchmark yet.

## If it is tried again

- Measure spec coherence *first*, on 4.0 output, before building
  anything to improve it. If the contradictions EP saw are real and
  frequent, quantify them; if a judge cannot find them reliably, a loop
  cannot fix them.
- Do not put a review methodology between the writer and the goal. A
  judge that reads for tidiness will narrow. If a second pass is wanted,
  make it a **gap sweep** — "list every stripped, undefined, or stubbed
  symbol the touched files reference" — which can only add.
- Benchmark the implement loop directly (multi-round verify → repair on
  the working tree) before assuming it is the part that works.
- Keep 4.0 as the baseline the whole way through; every change is a
  paired arm against it on the fixed harness, not a probe.

## Costs

Session total ≈ $430: leaky 5.0 run $84, clean 4.0 + 5.0 specs $156,
their inference $39, 5.1 panel $93 specs (incl. the `vo` probe) + $28
inference, plus ~$30 of timed-out probes and mutation/cost overlays.
About a fifth of it produced numbers that had to be retracted.

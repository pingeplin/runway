# 2606.0001 Blueprint 4.0 — From TDD Driver to Intent Producer + Referee

**Date:** 2026-06-04
**Status:** approved
**Author:** EP Lin
**Doc type:** RFC

> **Note on status.** The direction here is settled — this isn't a doc
> hunting for a decision. It exists to (a) preserve the *why* for future
> archaeology, and (b) pressure-test a breaking 4.0 redesign before it
> touches ~15 interlocking files. If the argument below has a hole, this
> is the cheap place to find it.

## TL;DR

Blueprint stops sitting in the driver's seat issuing turn-by-turn TDD
instructions. In 4.0 it does three things instead: **produces intent**
(a human-facing design doc and an agent-executable spec contract), **hands
implementation off to any coding agent** (Codex, Cursor, Claude Code, the
next one) to satisfy the contract however that agent works best, and
**referees the output** with fresh-context evaluators — regardless of how
the agent got there.

Concretely: `/run` and `/plan` are deleted. The pipeline collapses to
`/design → /spec → ⟦any coding agent implements⟧ → /verify → /commit`.
The spec becomes the keystone — the executable contract. A new `/verify`
referee enforces the one thing TDD's procedure actually bought us: tests
that fail when the code is wrong.

We are trading a strong, structural fail-first guarantee for a portable
protocol plus a post-hoc referee. That trade is the whole argument, and
the rest of this doc is about why it's worth it and where it can bite.

## The problem

Blueprint's back half (`/plan` → `/run`) is an elaborate TDD executor:
parse a slice DAG, walk slices in dependency order, batch-write tests,
dispatch a batch evaluator, verify all-fail, commit the failing batch as a
checkpoint, implement, run a bounded ≤5 fix loop, then an autonomous
refactor pass, then a verifier. It works. But it has two structural
problems that get worse over time, not better.

**1. Most of the choreography is model-compensation with a decay curve.**
The v3.4 CHANGELOG is explicit about *why* the machinery exists, and every
reason is a 2024–25 model weakness:

- IBM TDD-Bench Verified (2024): frontier models produce properly
  *failing-then-passing* tests only ~24% of the time without an enforced
  fail step.
- Chroma (2025): >30% accuracy drops from context rot starting ~50K
  tokens — the "all tests + all code + all fixes in one window" regime.
- Anthropic's own guidance: commit the failing tests first or the model
  quietly rewrites them to fit broken code.

These are real. They were real *for the models of that moment*. But
scaffolding built to compensate for a model weakness decays into pure
overhead as the weakness recedes — and betting against model improvement
is the one bet the field has lost every year (Sutton's bitter lesson).
We're already running this on Opus 4.8 with a 1M window. The choreography
that made a 2024 model safe is increasingly a cage around a 2026 one.

**2. The maintenance entropy is concentrated almost entirely in that back
half.** Walk the CHANGELOG from 3.4 to 3.7: sliced batching, the
batch-evaluator catch-rate tuning, skip-marker removal, comment-hygiene
rules pushed upstream, `/simplify` replaced by an autonomous `refactor-runner`,
per-agent model pinning. The design/spec front half barely moved across
the same span. We are paying a continuous tax to keep a procedure tuned
against a moving model target — and that procedure is the part with the
weakest claim to durable value.

**3. The procedure isn't portable, and portability is now the point.**
"Let any coding agent implement this" is a *protocol* problem, not an
*execution* problem. Codex, Cursor, Claude Code, and whatever ships next
each have their own opinionated internal loop. A skill that micromanages
"write the batch, commit the failing batch, fix loop ≤5 times" assumes one
specific agent that follows English procedure faithfully. The portable
interface across all of them is **intent** (what to build, what done means,
what a good test looks like) — not **procedure** (the order and cadence of
how to get there).

## Constraints shaping the solution

- **Tests must remain the durable behavioral contract.** This is
  non-negotiable and survives the redesign. Whatever replaces `/run` must
  not weaken the claim that the test suite *is* the spec.
- **No new tooling dependency at first.** The anti-vacuity mechanism (see
  below) has to work with zero external installs on day one. Real mutation
  tooling is desirable but cannot be a launch blocker.
- **Backward compatibility is not a goal.** This is a major version. We
  accept breaking in-flight plans/runs; the migration story is "finish or
  abandon in 3.x, start new work in 4.0."
- **The existing evaluator pattern is an asset to keep.** Fresh-context
  subagents that review an artifact with no sunk-cost bias are blueprint's
  best idea and the most reusable piece. The redesign should lean *harder*
  on them, not discard them.

## Proposed approach

### The architecture shift: driver → referee

Blueprint brackets the implementation instead of performing it.

```
/design  ──→  /spec  ──→  ⟦ any coding agent implements ⟧  ──→  /verify  ──→  /commit
 (human)      (agent-                                            (referee)
              executable
              contract)

utilities, called any time:  /refactor  ·  /review
```

The handoff happens in the middle. Blueprint owns the two brackets:
the **contract** going in and the **verdict** coming out. How the contract
gets satisfied is the implementing agent's business.

### What lives, dies, and transforms

| Component | Fate | Why |
|---|---|---|
| `/design` + `design-evaluator` | **Keep** | Human-facing decision artifact; source of the pipeline. |
| `/spec` + `spec-evaluator` | **Keep + elevate** | Becomes the agent-executable contract — the keystone. |
| `/run` | **Delete** | The driver. Its job is now the implementing agent's. |
| `/plan` + `plan-evaluator` | **Delete** | Existed only to order `/run`'s execution. Sequencing is the agent's call now. |
| `test-batch-evaluator` | **Delete** | A `/run`-internal slice-loop stage. |
| `refactor-runner` | **Delete** | A `/run`-internal autonomous cleanup stage. |
| `/proto` | **Delete** | A prescribed spike procedure — the kind of choreography 4.0 sheds. Prototyping is just using your coding agent directly. |
| `run-evaluator` | **Transform → `/verify`** | Becomes a standalone, agent-agnostic referee. |
| `/refactor` (+ `test-runner`) | **Keep as utility** | Beck two-hats, green-test discipline; agent-agnostic. Out of the core pipeline. |
| `/commit` (+ `commit-writer`) | **Keep as utility** | Agent-agnostic. |
| `/review` | **Keep as utility** | Agent-agnostic single-lens audit. |
| `test-desiderata.md`, `anti-patterns.md` | **Keep content, relocate role** | Now both the spec-bundled generator guidance *and* the `/verify` rubric. |

The headline: deleting `/run` cascades. `/plan`, two evaluators, and the
autonomous refactor stage all lose their reason to exist. That's not
collateral damage — it's the point. The back half was one machine, and
we're removing the machine, not trimming it.

### The spec becomes the contract (the keystone change)

Today the spec is "build-time scaffolding for `/plan`." In 4.0 it's the
artifact you hand to an arbitrary agent and say *build this*. That raises
the bar on what a spec must contain:

- **Inherited interface contract** from the design doc (API shapes, error
  taxonomy, breaking-change rules) — so the agent doesn't reinvent it.
- **Structured, machine-friendly acceptance scenarios** (Given/When/Then)
  — the behavioral core.
- **An explicit instruction to the implementing agent**, stated in the
  spec itself: *make every scenario pass with tests that would fail if the
  behavior were wrong.* The contract states its own success condition.
- **Bundled test-quality principles** (a tight extract of the desiderata +
  anti-patterns) so the generator has the guidance inline.
- **A Definition of Done** worded as exactly what `/verify` will check —
  the contract and the rubric are the same list, read from two ends.

The design doc stays human-facing and argumentative; the spec is its
machine-facing executable projection. One reasons; the other runs.

### `/verify` — the referee, and where anti-vacuity actually lives

This is the load-bearing part of the design, so it gets the most words.

Dropping TDD's *procedure* must not drop TDD's *anti-vacuity guarantee*.
What the fail-first commit actually bought was a single property: **a test
fails when the behavior it covers is wrong.** Lose that and you get the
Meta FSE'25 failure mode — 100% line coverage, 4% mutation score: a green
suite that proves nothing. And vacuous tests are insidious precisely
because they're *indistinguishable from good ones by inspection* — they
pass, they read fine, and the gap only shows up the day a real regression
slips through untouched.

The naive fix — "ship a *good tests* skill and let the implementing agent
read it" — does not work, for a reason worth stating plainly: **advisory
guidance under-triggers.** A skill the generator *may* consult is applied
inconsistently, and worse, "good test in isolation" is the wrong unit.
Vacuity is a property of the *suite's adversarial completeness*, not of any
single test's prose. Principles describe a good test; they don't certify
that the suite would catch a break.

So the guarantee has to be **enforced, post-hoc, by the referee** — and via
a mechanism that is *procedure-independent*, because we've thrown the
procedure away. `/verify` performs, on whatever any agent produced:

1. **Scenario coverage matrix** — every spec scenario maps to at least one
   test. (Inherited from `run-evaluator`.)
2. **Lightweight thought-mutation (the anti-vacuity check)** — for each
   covered behavior, the referee reasons: *what is the smallest change to
   the implementation that breaks this behavior, and would any existing
   test catch it?* If the honest answer is "no," the scenario is flagged
   as covered-but-vacuous. No tooling required; it's reasoning over the
   diff.
3. **Test Desiderata scoring** — Behavioral > Structure-insensitive >
   Readable > Specific > Deterministic > Isolated, against the same
   reference the generator was handed.
4. **Implementation-quality flags** — stale docstrings, restated-*what*
   comments, dead code (inherited from `run-evaluator` Step 5).

The thought-mutation check is the procedure-independent replacement for
fail-first. Fail-first proved non-vacuity *by construction, during the
build*; thought-mutation proves it *by inspection, after the build* — and
because it doesn't care how the code was produced, it works for any agent.
This also promotes the v3.4 CHANGELOG's deferred "mutation-test gate" from
an optional follow-up to the center of the architecture.

## Alternatives considered

**A. Status quo — keep driving.** Keep `/run` and the slice machinery,
keep tuning it per model release. Rejected: it doubles down on the part of
the system with the worst durability and the highest maintenance tax, and
it can't serve the "any coding agent" goal at all — the procedure only
binds one agent. The status quo is a bet that models stop improving.

**B. Keep `/run` as an optional Claude-native fast path, add `/verify`
alongside.** Tempting: don't break anyone, let Claude Code users keep the
choreographed path while external agents use the referee path. Rejected
for two compounding reasons. First, **double maintenance** — we'd carry
both the driver and the referee, and the driver is exactly the
high-entropy half we're trying to shed. This reason alone is sufficient to
reject B. Second, and independently, **a Claude-only driver contradicts
the thesis**: portability is the whole pitch, and you can't credibly claim
an agent-agnostic referee as the new identity while shipping a driver
bound to one agent. Keeping `/run` would also force `/verify` to serve two
provenance models — "our own disciplined output" and "arbitrary agent
output" — splitting the verification contract we're trying to unify. That's
a coherence cost, not a matter of taste. If the referee architecture is
right, it's right for Claude Code too; there's no reason to exempt our own
agent from it.

**C. Advisory "good tests" skill only, no referee enforcement.** The
lightest possible version: produce design + spec, ship a test-quality
skill, trust the agent. Rejected: this is the under-triggering /
vacuity-blind failure mode described under `/verify` above. It's the
version that *looks* like the others but quietly removes the one guarantee
that justified TDD in the first place. Without an enforced post-hoc check,
"satisfy the spec, write good tests" optimizes straight toward the
easiest-to-pass tests.

The chosen approach is B's portability without B's double maintenance,
plus C's lightness without C's missing guarantee.

## Trade-offs we are accepting

This is the section that has to be honest, because the chosen path gives
up real things:

- **We lose the strong, structural fail-first guarantee.** v3.4's
  failing-test commit proved non-vacuity *by construction*. `/verify`'s
  thought-mutation proves it *by inspection*, which is weaker: it depends
  on the referee's reasoning quality, and a lazy or fooled referee passes
  a vacuous suite. We are betting that a fresh-context referee with an
  explicit mutation rubric catches *most* of what fail-first caught by
  force — and that real mutation tooling later closes the rest.
- **We lose the per-slice commit trail.** The granular failing-test →
  implementation checkpoint history is gone; the implementing agent
  commits however it commits. We get portability; we lose a clean,
  uniform archaeology of how each behavior was built. This loss is partly
  illusory, though: the v3.4 empirical study (8 katas, 2026-05-18) already
  found the per-slice impl-commit pattern degrading on structurally complex
  features — on the Markdown→HTML task, tests committed per slice but
  implementation batched at the end. The trail was already most fragile
  exactly where features are hardest, which is where it would have mattered
  most.
- **We depend on referee quality as a single point of failure.** In 3.x,
  quality came from many small gates. In 4.0, a large share rides on
  `/verify`. If the referee is weak, the whole guarantee is weak. This
  argues for investing in `/verify`'s rubric and, eventually, the tooling
  backstop.
- **We can no longer assume the implementing agent followed *any*
  discipline.** The referee must treat the input as adversarial — code of
  unknown provenance — not as "our own careful output." That's a mindset
  change for the evaluator prompts.

## Riskiest assumption

**That lightweight thought-mutation reasoning catches vacuous tests
reliably enough to stand in for the fail-first guarantee — without real
mutation tooling.** If a fresh-context referee, asked "what's the smallest
break that no test would catch," turns out to rubber-stamp vacuous suites
in practice (plausible — it's a reasoning task with no ground truth), then
4.0 ships with a weaker correctness guarantee than 3.x and we won't
necessarily know until a regression escapes. Mitigation: treat the real
mutation-tooling follow-up as a *scheduled* hardening, not an open-ended
"someday," and gate full trust in `/verify` on a benchmark of seeded
vacuous suites that measures the referee's catch rate — the same benchmark
named under success criteria and follow-ups. Until that catch rate is
measured, `/verify`'s verdict is treated as advisory-strong, not proven.

## How we'll know it worked

- **Portability, demonstrated:** the same spec is handed to two different
  coding agents (e.g., Claude Code and one other) and both produce suites
  that pass `/verify` — proving the contract, not the procedure, carries
  the intent.
- **Referee catch rate:** on a set of deliberately seeded vacuous suites,
  `/verify`'s thought-mutation flags ≥ a target fraction (to be set when
  the benchmark exists). This is the number that tells us whether the
  riskiest assumption holds.
- **Maintenance entropy drops:** post-4.0 CHANGELOG churn in the
  (now-deleted) `/plan` + `/run` surface area goes to zero, and total
  plugin surface area shrinks by a measurable, pre-committed amount — per
  the "what lives, dies, transforms" table, 2 skills (`/run`, `/plan`) and
  3 agents (`plan-evaluator`, `test-batch-evaluator`, `refactor-runner`)
  are deleted outright and `run-evaluator` is renamed/transformed into the
  `/verify` referee (still one agent), taking the agent count from 8 to 5.
  The deleted-machinery reference files drop with them (`review-plan.md`,
  `review-test-batch.md` removed; `review-impl.md` is kept but rewritten —
  its slice/run-loop phases stripped, its implementation-quality flagging
  retained as the referee's check 4).
- **No silent correctness regression:** spot-checking 4.0-built features
  against their specs surfaces no higher rate of escaped behavioral bugs
  than 3.x did on comparable work.

## Out of scope

- **Real mutation-testing integration** (mutmut, Stryker, PIT). Explicit
  follow-up; the launch uses thought-mutation only. The architecture is
  designed so this drops into `/verify` as a strengthening, not a rewrite.
- **A machine-readable spec serialization** (JSON/YAML contract for
  programmatic agent ingestion). 4.0's spec stays Markdown-with-structure;
  a stricter format is a later question if external-agent ingestion
  demands it.
- **Multi-agent / agent-colony orchestration** (handing one spec to N
  agents and choosing the best result). The referee architecture *enables*
  this later, but 4.0 ships the single-agent handoff.
- **A migration tool** from in-flight 3.x plans/runs. The migration story
  is "finish in 3.x or restart in 4.0," not automated conversion.

## Follow-ups

- Integrate real mutation tooling into `/verify` (hardening the riskiest
  assumption).
- Build the seeded-vacuous-suite benchmark to measure referee catch rate.
- Revisit a machine-readable spec format if/when programmatic external-agent
  ingestion becomes a real workflow.
- **Give `/verify` an inspection mode for non-code deliverables.** The
  referee currently hard-requires a runnable test suite (Step 1), so it
  cannot referee specs whose acceptance scenarios are file-inspection
  assertions — e.g. prompt/skill/doc engineering, like this very redesign.
  `/verify` should detect "scenarios are inspection assertions, not
  behavioral tests" and switch to checking them directly rather than
  dead-ending on a missing suite. (Surfaced while dogfooding 4.0 on itself.)

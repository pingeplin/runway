# 2609.0004 Hooks as Evidence Collector, Not Gate

**Date:** 2026-09-16
**Status:** draft
**Author:** EP Lin
**Doc type:** RFC

## TL;DR

Ship a Claude-Code-only `PostToolUse` hook that records what the session actually did — which test commands ran, what they returned, and in what order relative to edits — into a per-session ledger. `/verify` reads that ledger when it exists and uses it to *upgrade* its anti-vacuity verdict from reasoned to observed, and to prioritise where it spends its reasoning. When the ledger is absent, `/verify` behaves exactly as it does today.

The hook never blocks anything. The principle is not "blueprint never gates" — it plainly does, at `/verify`. It is **the deterministic layer observes; the reasoning layer judges.** A hook cannot tell a refactor from a missing test, so it does not try.

## The problem

`/verify`'s headline check grades itself as unproven. From `skills/verify/SKILL.md`:

> **Honest verdict.** Until real mutation tooling backs check 3, the verdict is *advisory-strong*, not *proven* — say so. Don't launder a reasoning pass into a guarantee.

Check 3 is the thought-mutation pass, and `agents/referee.md` calls it "the check that replaces TDD's fail-first guarantee, and it is the reason you exist." So the plugin's load-bearing quality gate rests on an LLM reasoning about a counterfactual — *would any test fail if I broke this?* — with no observation of what actually happened.

Meanwhile the information that would ground it is being generated and thrown away. Every `pytest` invocation in the session, its exit code, and whether it ran before or after the implementation edit are all visible to a `PostToolUse` hook and all discarded when the turn ends.

[ASSUMPTION: that `PostToolUse` on `Bash` hands the hook the command's exit status as a field, not just its combined output text. Nothing in this repo verifies the payload shape. If exit status has to be recovered by parsing output, the field this design calls load-bearing needs a per-runner parser, and the classifier's scope grows accordingly.]

**The FeatureBench harness is not a second consumer, and cannot be.** `scripts/03_infer.py` runs `fb infer --agent claude_code`, so implementation happens inside FeatureBench's container with vanilla Claude Code and no blueprint plugin; the plugin is only used host-side in the Arm B spec pre-stage. The control-arms stage goes further and *fails the task* if any blueprint plugin, skill or agent loads. A plugin-shipped hook therefore produces no ledger in any FeatureBench run. This design serves `/verify` only.

## Constraints

**The 4.0 architecture is the binding one.** Blueprint deleted `/run` on the argument that "intent is portable; procedure is not." Hooks are procedure, and they exist only in Claude Code. Any design that makes blueprint *depend* on a hook contradicts the thing that makes blueprint worth using with Codex, Cursor, or a human.

**`referee.md` explicitly refuses provenance.** Its opening instruction is "Do not assume the tests were written before the code, do not assume they were written to fail first, do not assume good faith." A ledger hands the referee precisely the provenance it is told to distrust. This is not fatal, but it means the ledger must be evidence the referee *evaluates*, not a fact it *trusts* — and it must never soften the adversarial stance for code it cannot see the history of.

**Most runs will have no ledger.** Any implementation produced by another agent, in another tool, or in a session before the hook was installed. Absence is the common case, not the edge case.

## Proposed approach

### What gets recorded

A `PostToolUse` hook on `Bash`, `Edit` and `Write` appends one line per event to `.blueprint/ledger/<session-id>.jsonl`:

```jsonc
{"ts": "...", "kind": "test_run", "cmd": "pytest tests/test_rate_limit.py",
 "exit": 1, "tests_failed": ["test_rejects_over_limit"], "cwd_sha": "..."}
{"ts": "...", "kind": "edit", "path": "src/rate_limit.py", "sha_before": "...", "sha_after": "..."}
```

The hook classifies a Bash command as a test run by pattern (`pytest`, `go test`, `npm test`, `cargo test`, …) and extracts failures where the runner's output makes that cheap. It does not parse every framework's output format; an unparsed test run still records `exit`, which is the load-bearing field.

### What `/verify` does with it

Per acceptance scenario, the referee asks one new question before its thought-mutation: **did a test covering this scenario ever go red, then green, with an implementation edit in between?**

- **Yes** → the scenario has observed fail-first evidence. Report it as `observed`, and spend proportionally less reasoning there.
- **No, and a ledger exists** → the test never failed in this session. That is a *signal*, not a verdict — the test may predate the session. Flag it as unobserved and reason harder.
- **No ledger** → today's behaviour, unchanged. Every scenario gets the full thought-mutation pass and the verdict stays *advisory-strong*.

The verdict vocabulary gains one level. It does not lose any.

### Why the deterministic layer must not judge

A gate needs to answer "should this change have had a failing test first?" That question has no cheap correct answer: refactors, spikes, doc edits, dependency bumps and typo fixes all legitimately answer *no*. shunt's hook can block outright because its question is stateless — is this file over 350 lines — and it is right every time, which is why 34 deterministic cases cover it. Ours is not stateless, so the judgement belongs in `/verify`, which already has the spec, the diff and the reasoning budget to make it.

Two consequences follow, and they are the real argument:

**A wrong gate costs the observation layer too.** Gate and collector are the same hook. A user who disables it after one bad block loses the evidence stream with it — so the collector's survival depends on the gate never existing.

**A gate produces no data about itself.** A blocked commit leaves no record of whether blocking helped; the counterfactual is destroyed by the intervention. Observation is measurable, enforcement is not — which is why observation comes first even on a phased reading.

## Alternatives considered

**Block `git commit` until the test suite passes.** The plain version, and the one originally asked for. It needs no spec, no marker and no blueprint state — just a runner and an exit code, which is why `pre-commit` already does it well. Rejecting it is not a claim that it is a bad idea; it is a claim that it is *not this plugin's idea*, adds nothing blueprint-specific, and would put a blocking behaviour on the same hook the collector depends on.

**Block `git commit` until `/verify` has passed for this patch.** The blueprint-specific version, and the genuinely tempting one. It needs a marker recording which spec was verified against which patch — and the cache key has to include the patch, not just the spec. The FeatureBench stale-verdict bug is the worked example of getting that wrong: a verdict keyed only on `(arm, task_id)` was reused to referee a patch it had never seen, silently. That is a real hazard, but it is an argument for *care*, not for *never* — the stronger objection is the unmeasurability above.

**Wait for real mutation tooling** (`mutmut`, `cosmic-ray`, Stryker). This is what `verify/SKILL.md` names as the thing that would make check 3 proven, and it would be strictly stronger evidence than a ledger. It is also per-language, slow enough to change the shape of `/verify`, and does not answer the fail-first question at all — it grades the suite as it stands, not how it came to be. Worth doing later; not a substitute.

**Do nothing.** Defensible. The referee's reasoning has never been shown to be *wrong* — it has only been shown to be unverified. The case for acting now is that the evidence is free, already being produced, and currently discarded.

## Trade-offs this accepts

We accept a Claude-Code-only capability in a plugin that sells agent-agnosticism, in exchange for grounding the one check the plugin admits is unproven. The mitigation is strict: the ledger may only ever add a verdict level, never remove the reasoning pass, so a Codex user's `/verify` is never worse than it is today — it is just never better either.

We also accept that a red→green transition is **weaker evidence than it sounds**. A test can go red, then green, and still be vacuous — asserting something trivially coupled to the implementation that was just written. 4.0 deleted fail-first as *procedure*, not as a guarantee — the CHANGELOG credits it with buying non-vacuous tests and hands that job to the referee because the procedure was not portable. Even so, this design does not restore a stronger guarantee than mutation reasoning; it adds a cheap, orthogonal one. Selling it as "now proven" would be the laundering `verify/SKILL.md` warns against.

## Riskiest assumption

**That scenario-to-test attribution is tractable from the ledger.** The ledger records that `test_rejects_over_limit` failed and later passed. Mapping that to acceptance scenario 3 requires the same fuzzy matching the referee already does in its coverage step — and if that mapping is wrong, the design produces confidently mislabelled `observed` verdicts, which is worse than no ledger at all.

If this proves unreliable, the fallback is to drop per-scenario attribution and report the ledger at suite granularity only: "some test went red then green during this session" is a much weaker claim but a safe one.

A smaller known gap: `edit` events come from the `Edit` and `Write` tools, so an implementation change made through Bash — `sed -i`, `git apply`, `git checkout` — is invisible, and a genuine red→green cycle around one will be missed. Missing evidence degrades to "unobserved", which is the safe direction, but it is not neutral: it will make disciplined sessions look undisciplined.

## How we will know it worked

- **Attribution accuracy ≥ 90%** on a hand-labelled set of 20 scenarios from real blueprint-driven sessions in this repo — scenario marked `observed`, and a human agrees the named test really covers it. FeatureBench cannot source this set, per the Problem section; the sessions have to be produced deliberately.
- **The hook's classifier is exercised by deterministic cases** — test-command detection, non-test Bash, piped commands, exit-code extraction — in the style of shunt's 34 hook cases. Note this needs a runner that does not exist yet: `plugins/blueprint/evals/` today drives real agents through `claude plugin eval`, where "free" describes the graders, not the run. Piping JSON into a hook script is a second, cheaper harness.
- **Zero behavioural change with no ledger present** — a fixed set of `/verify` runs on a ledger-free repo produce the same verdicts as today. The triggering suite is not the oracle for this: its own README calls a case moving between 2/3 and 3/3 noise, which is not a pass/fail signal.

## Out of scope

- Any blocking or prompting behaviour in the hook itself (a `Stop` reminder, a commit gate). The judgement layer stays in `/verify`. If L0 data later shows a gate would have fired correctly, that is a new decision with its own doc — not a phase of this one.
- Real mutation tooling.
- Porting the ledger to Codex or Cursor.
- Ledger retention, rotation, or anything touching a repo's git history.

---

**Things to confirm or correct before this goes for review:**

1. **`.blueprint/ledger/` as the location** — assumed, alongside `.blueprint/specs/`. Needs a `.gitignore` decision: I have assumed the ledger is local-only and never committed.
2. **Session-scoped, not spec-scoped** — one file per session rather than per spec. Simpler for the hook, but means `/verify` must locate the relevant session(s) itself.
3. **That `/verify` being the only consumer is acceptable.** The FeatureBench consumer was cut as infeasible, not descoped by preference — the harness runs vanilla Claude Code in a container and its control stage fails tasks when blueprint loads. If you want ledger data from benchmark runs, that is a harness change, not a plugin change, and it breaks the stage-14 control invariant for Arm A.
4. **The framing is now "deterministic observes, reasoning judges"**, not "never blocks" — the original wording claimed a principle where the Out of Scope section conceded a sequence. If you would rather state the commit gate as an explicit future phase, say so; it changes the argument, though not the code.
5. **Test-runner coverage** — assumed pytest/go/npm/cargo pattern matching is enough to start. A polyglot repo may need configuration, which is a different design.

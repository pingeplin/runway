## Terms

| term | meaning |
|---|---|
| mask | The code a FeatureBench task strips from the repository to create the task. |
| oracle | The stripped code plus the hidden tests that grade the result. |
| pass rate | Share of a task's hidden tests that pass. Panel figures are means over the panel's tasks. |
| resolved | Every hidden test of the task passes. |
| cell | One task × one arm in one run. |
| stage NN | Script `NN_*.py` of the FeatureBench harness. |
| fence | A spec statement that puts code or behaviour out of scope. |
| oracle recall | Share of stripped `def`/`class` names that a spec names in code formatting (stage 12). |
| fenced∩oracle | Stripped names that a spec fences (stage 12 heuristic; stage 13 LLM listing). |
| kill rate, stage 07 | Share of LLM-chosen mutants of the agent's patch caught by the test files the patch touched. Mutants are chosen per cell. Cells with no tests score 0. |
| kill rate, oracle-anchored | Share of fixed mutants of stripped reference lines caught by the agent's own tests. A mutant is kept only if the hidden tests catch it. Cells with no tests score 0. |
| referee | The `/verify` skill, run headless. |
| arm A | The implementing agent gets the problem statement only. |
| arm B | The implementing agent gets the problem statement plus a `/spec`. |
| arm C | A second attempt from the pristine repository, given B's patch plus the `/verify` verdict. |
| arm C0 | As C, but given one generic self-review sentence instead of the verdict. |
| generic brief (arm A_plan) | An implementation brief written by the same model with blueprint disabled. |

## Goals the evaluation must serve

EP, 2026-09-18:

> 我最主要的目標是透過 design doc 來對比較複雜的功能做詳細的規劃，並將這份文件作為歷史文件；spec 則是比較偏向產生 test cases，引導 coding agent 做完工作，原則上是可以不會寫入 git history 的文件。

Translation: The main goal is to use a design doc to plan a complex feature in
detail and keep it as a historical document. A spec leans toward producing
test cases and guiding a coding agent to finish the work, and in principle
does not need to enter git history.

This document judges v1 against these criteria, which are derived from the
goal above:

| artefact | criterion |
|---|---|
| Design doc | A later reader can reconstruct why the decision was made. |
| Spec | Its tests catch defects, and the agent builds what was asked, no less and no more. |

## Findings

1. **Every spec effect above noise came from restoring stripped code.**
   - Lift: on `lombscargle_multiband` the 4.0 spec named a second stripped
     module. It scored 0.96 in all four runs of that spec. The task scored
     0.03 with no spec, the hint, the generic brief, the 08-16 spec and the
     Ouroboros specs.
   - Regression: the Ouroboros A spec fenced stripped neighbours. It scored
     0.00 on `vo` and 0.03 on `lombscargle_multiband`, against 0.95 and 0.96
     for the 4.0 spec.
   - Within noise, same cause: on `vo` (09-18) the Out of Scope spec scored
     0.01 against the 4.x spec's 0.39. The agent left a stripped module
     unrestored (`astropy/utils/xml/check.py`) that no spec named.
2. **FeatureBench cannot penalise over-reach or pose an underdetermined
   requirement.** The hidden tests fix the requirement, and no hidden test
   fails when the agent builds extra. It cannot distinguish scope discipline
   from under-building.
3. **Stage 07 graded the spec's tests unreliably.**
   - Mutants were chosen per cell by an LLM, so arms were not graded on the
     same mutants.
   - Stage 07 ran every test file a patch touched. It excluded a cell when any
     test in those files failed before mutation (`baseline_red`). On
     09-16 this excluded 4 of the 7 cells where the agent wrote tests, and
     cells with no tests scored 0, so 1 cell per arm was graded, and it was
     the same task (`basic_rgb`).
   - The C-vs-C0 direction reversed, on the no-tests = 0 figure:
     - C 0.50 vs C0 0.40 in the 08-15 pilot (N=3, sonnet-4-5, leaky).
     - C 0.46 vs C0 0.59 in the 08-16 panel (leaky, retracted).
   - The oracle-anchored grader exists only as a post-hoc audit
     (`reports/2609_armc_clean_astropy_n5/referee_audit/layer3/`).
4. **Coherence, testability, grounding and smell density did not predict
   pass rate.**
   - Coherence (LLM judge): ρ 0.00. The same spec moved by up to 4
     contradictions between judge repeats (`reports/2609_doc_quality_validation/`).
   - Testability ≥ 0.85 and grounding ≥ 0.97 on every spec (same report).
   - Smell density: ρ −0.34. 16 of 20 sampled hits were in descriptive prose,
     model-classified (`reports/2609_smell_density_validation/`).
5. **Fencing stripped code lowered pass rate beyond noise once.**

   | spec | pass rate | versus | within noise |
   |---|---|---|---|
   | Ouroboros A (fences stripped neighbours) | 0.37 | 4.0 spec 0.84 | no |
   | Ouroboros B (loop forbidden to narrow scope; still fenced `get_err_str`) | 0.70 | 4.0 spec 0.84 | not assessed |
   | Generic brief (contains "do not touch" fences) | 0.40 | no document 0.48 | yes, under 0.15 |
   | Out of Scope section, 09-18 | `vo` 0.01 | 4.x spec 0.39 | yes, `vo` swings 0.55 |

6. **Instrument defects found 08-15 → 09-18:**
   - Oracle leak through the working tree, in an unmasked run before the
     pilot, archived out of the repository.
   - Oracle leak through git history. It retracted 2 published results.
   - A cached referee verdict was reused across different patches.
   - `fb` installs Claude Code `@latest` in the container unless
     `CLAUDE_CODE_VERSION` is pinned.
   - Symbol-level fence metrics:
     - missed fences stated by line range.
     - matched `FieldRef.get_ref` to the stripped `ParamRef.get_ref` by bare
       name.
     - miscounted boundary symbols under the new Out of Scope template.
   - Plugin defect, found by the harness: headless `/verify` produced no
     output (fixed in PR #21).
7. **Per task, run-to-run noise (0.55 on `vo`) exceeded every spec effect
   except the lift and the regression in finding 1.**
   - Re-running the same spec moved `vo` by 0.55.
   - With the same specs, the agent wrote tests on 3 of 5 tasks on 09-10 and
     on 1 of 5 on 09-16.
   - Every panel after the pilot was N=5, astropy only, one run per arm.
   - All-in cost per task: B $20.98, A $2.55 (`reports/2609_control_arms_astropy_n5/`).
8. **The evaluation was not independent.** The plugin's authors chose the
   tasks, harness, metrics and judge. Every model involved was Claude: the
   spec writer, the implementing agent and the judge.
9. **Instrument size did not predict decisiveness.**

   | instrument | size | produced a verdict |
   |---|---|---|
   | BLUEPRINT-BENCH v1 | ~9,800 lines of Python, plus 616 tests | no |
   | FeatureBench harness | ~5,800 lines of Python | directional results; defects in finding 6 |
   | Transcript analysis | 260 lines of Python; $0 | yes: rejected `2609.0004` before implementation |

## Lessons learned

1. Before building an instrument, name the decision its number can change
   (finding 9).
2. Measure each artefact's own job. Treat pass rate on another benchmark's
   task shape as a guardrail only (findings 1, 3).
3. Choose tasks where both under-building and over-reach lose points
   (findings 2, 5).
4. Run the control at least twice before any treatment. Do not run a
   treatment whose expected effect is smaller than the control's run-to-run
   swing (finding 7).
5. Treat any metric computed from the document text alone as diagnostic
   until it predicts an outcome on a corpus with known results. Use an LLM
   judge only for listing and quoting, with measured self-agreement
   (finding 4).
6. Keep oracles outside the workspace by construction. The oracle leaked
   twice (finding 6).
7. Run the cheapest tier first. The repo's own transcripts and design docs
   come before paid benchmarks (finding 9).
8. Build one small, disposable instrument per question (findings 6, 9).
9. Keep what caught defects or controlled confounds (findings 3, 6):
   - pre-registered reading rules
   - same-day pairing with a pinned agent version
   - isolated per-arm harness copies
   - cache keys that include every input
   - mutation-checking every grader

## Results that stand

Benchmark rows are directional only: N ≤ 5 tasks, astropy (the pilot also
used metaflow).

| result | source |
|---|---|
| Without a spec, the agent wrote no tests: A 0 of 3 tasks, 0 of 5 tasks. | `reports/2608_pilot_n3/mutation_report.md`, `reports/2608_scale_astropy_n5/mutation_report.md` |
| Oracle-anchored kill rate: C 0.39, C0 0.23, B 0.18. The verdict's claims covered 11 of 176 failing hidden tests. No hidden-test gain traced to the verdict. | `reports/2609_armc_clean_astropy_n5/referee_audit/` |
| Same day: the Ouroboros A spec, which fences stripped neighbours, scored 0.37 against 0.84 for the 4.0 spec. The Ouroboros B spec, whose loop was forbidden to narrow scope and which still fenced `get_err_str`, scored 0.70. | `reports/2609_clean_paired_astropy_n5/` |
| No agent edited a test to turn a suite green: 0 of 43 red→green cycles, 116 sessions. | `2609.0004` |
| A skill-triggering grader must match the invocation shape (`"skill":"blueprint:spec"`), because the trace lists every available skill. | `archive/evals-v1:plugins/blueprint/evals/README.md` |

## Requirements for the next pipeline

| goal | requirement |
|---|---|
| Spec → tests | A deterministic grader: fixed mutants of a reference implementation, run against the tests the spec produced. |
| Spec → finished task | Tasks where under-building and over-reach both lose points. |
| Design doc → record | A reconstruction test on real design docs with known later outcomes, starting with `docs/designs/`: a reader given only the doc answers fixed questions on why the chosen option won and what would invalidate it, and the answers are scored against the author's. |

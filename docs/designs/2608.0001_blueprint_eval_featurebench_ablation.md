# 2608.0001 Blueprint Eval MVP — Paired Spec Ablation on FeatureBench

**Date:** 2026-08-15
**Status:** approved (MVP scope)
**Author:** EP Lin · drafted with Claude
**Doc type:** RFC

> **Note on status.** The direction (outsource task authoring + oracle +
> scoring to an existing benchmark; measure blueprint as a paired
> ablation) was settled in discussion. This doc pins the MVP scope and
> the load-bearing implementation decisions so the harness can be built
> and iterated without re-litigating them.

## TL;DR

We stop hand-authoring eval tasks for blueprint. Instead, the MVP
harness measures **one number**: does handing an implementing agent a
blueprint-produced spec improve its resolved rate on
**FeatureBench lite** (30 real feature-development tasks, docker-scored
against hidden fail-to-pass tests)?

Design: a **paired two-arm ablation** on the same tasks, same
implementing agent, same model —

- **Arm A (control):** `fb infer` on the official dataset. The agent
  gets the original problem statement.
- **Arm B (treatment):** a pre-stage runs blueprint v4 `/spec`
  headlessly against each task's codebase, then `fb infer` runs on a
  **locally rewritten copy of the dataset** whose `problem_statement`
  is the original text **plus the spec**. Everything else is identical.

Both arms are scored by the unmodified `fb eval` against the **official**
dataset (predictions carry only `instance_id` + `model_patch`, so the
treatment cannot leak into scoring). The report is a per-task paired
table plus an exact McNemar test on discordant pairs.

## The problem

The v3.3.1→v3.4.0 comparison (`plugins/blueprint/references/eval-methodology.md`)
proved we can run a version comparison, but it doesn't scale: we author
the tasks (8 katas), author the hidden oracle, hand-pick mutations, and
babysit interactive sessions via tmux+cron. Three costs dominate:

1. **Task credibility** — small katas don't look like the feature work
   blueprint v4 claims to help with, and we ran out of good tasks.
2. **Oracle authorship** — single-rater bias, per-task effort.
3. **Orchestration** — interactive gates × 16 cells was the bulk of the
   wall-clock pain.

An existing benchmark solves 1 and 2 outright and most of 3.
FeatureBench is the best fit available in 2026: feature-level tasks
derived from real repos (not bugfix-shaped issues whose descriptions
are already spec-quality), execution-based scoring in per-task docker
images, a 30-instance `lite` split for pilots, and enough headroom
(SOTA ~11% on full) that a real spec effect won't be crushed by a
ceiling. Its harness natively runs Claude Code as the implementing
agent, which removes our biggest custom-code risk.

## Proposed approach

```
                        ┌─ Arm A ─────────────────────────────┐
official HF dataset ──►│  fb infer (claude_code, model M)     │──► output_A.jsonl ─┐
  LiberCoders/          └──────────────────────────────────────┘                    │
  FeatureBench (lite)                                                               ├─► fb eval ──► report_{A,B}.json
        │               ┌─ Arm B ─────────────────────────────┐                    │      (official dataset,
        │  per task:    │  fb infer (same agent, same model)  │──► output_B.jsonl ─┘       hidden F2P tests)
        ├─► docker cp   └──────────────────────────────────────┘                                   │
        │   /testbed ──► claude -p + blueprint /spec ──► spec.md                                   ▼
        │                                    │                                            05_report.py
        └────────────────────────────────────┴─► local dataset dir                    paired table + McNemar
                                                 (problem_statement += spec)
```

Six numbered stages, each restartable, state on disk under
`evals/blueprint-featurebench/`:

- **00_setup** — install `featurebench` (from GitHub; not on PyPI),
  `fb pull --mode lite` to pre-pull images, sanity-check docker +
  `claude` auth.
- **01_make_specs.py** — for each pilot task: extract the task's
  codebase **from its own docker image** (`docker create` +
  `docker cp :/testbed`), run `claude -p` in that workspace with the
  blueprint plugin, producing `.blueprint/specs/*.md` via the `/spec`
  skill, non-interactively. Save spec text + cost/duration metadata per
  task. A task whose spec stage fails is recorded and **excluded from
  both arms** (paired design requires both cells).
- **02_make_dataset.py** — load the official split, append each spec to
  its task's `problem_statement`, write a **local HF dataset directory**
  (JSONL + `README.md` with YAML `configs:` declaring the split name)
  that `datasets.load_dataset(<dir>, split=...)` — and therefore
  `fb infer --dataset <dir>` — accepts unchanged.
- **03_infer.sh** — two `fb infer` runs (Arm A: official dataset name;
  Arm B: local dir), same `--agent claude_code`, same `--model`, same
  task-id list.
- **04_eval.sh** — two `fb eval` runs against the **official** dataset.
- **05_report.py** — per-task paired table (resolved A/B, pass rates,
  spec cost), discordant-pair counts, exact McNemar p-value (stdlib
  binomial — no scipy), honest caveats block (N, single seed).

### Load-bearing decisions

**Reuse `fb infer` for both arms; inject the treatment through the
dataset, not through a fork of the harness.** The only difference
between arms must be the text the implementing agent reads. Rewriting
`problem_statement` in a local dataset copy achieves that with zero
patched FeatureBench code, and keeps both arms on the identical
docker-env execution path (agent can run the repo's tests while
implementing — fidelity our own infer loop would lose).

**Spec stage reads the codebase from the task's docker image, not from
a git clone.** `docker cp` of `/testbed` guarantees the spec is written
against exactly the code state the implementing agent will see, and
avoids depending on dataset fields (repo URL, base commit) we have not
verified. The images are required for infer/eval anyway.

**Spec is appended, not substituted, and scoring never sees it.**
Arm B's problem statement = original + spec (augmentation treatment, no
precedence clause — if the spec misleads the agent, that is exactly the
signal we are measuring). `fb eval` loads instances from the official
dataset and reads only `instance_id`/`model_patch` from predictions
(`harness/constants.py`), so the treatment cannot contaminate scoring.

**Headless `/spec` via `claude -p`.** The prompt template instructs the
skill to run without approval gates; permission mode and extra CLI args
are configurable. This is the MVP's riskiest integration point (see
below) and is isolated in one script with a `--claude-cmd` override so
it can be smoke-tested with a mock.

## Alternatives considered

- **SWE-bench Verified / Pro as the panel.** Rejected for MVP:
  Verified is saturated (~90%, ceiling crushes deltas) and
  bugfix-shaped — issue text is often already spec-grade, so the spec
  stage has nothing to add. Pro is a reasonable *second* panel later.
- **Write our own infer loop (clone + `claude -p` + `git diff`) and use
  only `fb eval`.** More control, but both arms lose the in-container
  test-running environment, and we'd re-implement patch extraction,
  retries, and logging that `fb infer` already has. Rejected while the
  dataset-injection route works; documented as the fallback if
  `fb infer --dataset <local dir>` proves brittle.
- **Include Arm C (`/verify` loop) now.** Deferred. It needs a
  same-iteration-count control arm to be attributable (extra arm ×
  tasks × docker time), and the MVP question is upstream: does the spec
  help at all?
- **Keep authoring our own kata panel.** Rejected as the primary
  instrument for the reasons in "The problem"; survives as a future
  overlay for the dimensions FeatureBench can't see (agent-written test
  quality / mutation score), which no external benchmark scores.

## Trade-offs we are accepting

- **FeatureBench measures end-to-end correctness only.** Test quality,
  anti-vacuity, design-argument quality — the referee half of
  blueprint's value — are invisible to it. MVP accepts this; the
  mutation-score overlay is a follow-up.
- **N=30 × 1 seed is a pilot, not a verdict.** With ~11%-level resolve
  rates, expect single-digit discordant pairs; the report must present
  the McNemar p-value as directional. Scaling to `fast` (100) or
  multi-seed is a config change, not a redesign.
- **Spec cost is real.** The report carries per-task spec-stage cost
  (USD + wall time) next to the outcome so "+X resolved at +Y cost" is
  the headline shape, never bare accuracy.
- **Model contamination** (models may know these repos) dilutes both
  arms equally under pairing; it biases levels, not the A/B delta.

## Riskiest assumption

**`/spec` runs usefully in one non-interactive `claude -p` pass.** The
skill was written for interactive use with approval gates and an
evaluator subagent. If headless runs stall on a gate, ask questions, or
emit no spec file, Arm B dies at stage 01. Mitigations: prompt template
explicitly forbids questions and gates; `--claude-args` passthrough for
permission mode; per-task failure recorded without aborting the panel;
and stage 01 is the first thing to pilot on 2–3 tasks before burning
the full split. If headless `/spec` fundamentally can't work, the fix
belongs in the *plugin* (an explicit headless/eval mode) — which would
itself be a useful v4.x deliverable.

## How we'll know it worked

The MVP goal is **the harness runs end-to-end on v4 and produces a
readable result**, not that the result is flattering:

1. Stage 01 produces specs for ≥80% of pilot tasks without manual
   intervention.
2. Both arms complete infer + eval on the pilot subset; `05_report.py`
   emits the paired table.
3. The report states resolved A vs B, discordant pairs, p-value, and
   per-arm cost — enough to decide whether scaling to `fast`/multi-seed
   is worth it.

## Out of scope (MVP)

Arm C (`/verify`), `/design` stage (feature tasks may warrant it, but
one treatment at a time), mutation-score overlay, multi-seed, SWE-bench
Pro second panel, blueprint version-vs-version comparison (the harness
is built for it — swap the plugin version and rerun Arm B — but the
first run is spec-vs-no-spec), leaderboard-grade rigor.

## Follow-ups

1. Pilot stage 01 on 2–3 tasks; fix the headless `/spec` path first.
2. Full lite run; read the failure taxonomy (spec-wrong vs impl-wrong).
3. If signal: scale split/seeds; add Arm C with iteration-count control.
4. Mutation-score overlay on agent-written tests (reuse the strategic-
   mutation method from `eval-methodology.md`).
5. Consider a first-class headless mode in blueprint itself.

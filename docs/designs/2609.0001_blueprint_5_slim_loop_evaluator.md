# 2609.0001 Blueprint 5.0 — Slim Plugin, One Loop, One Evaluator

**Date:** 2026-09-10
**Status:** implemented
**Author:** EP Lin
**Doc type:** RFC

> **Note on status.** The direction is settled by the plugin's only user
> after three months on 4.0. This doc exists to pressure-test the cuts
> before they touch ~20 files, and to record *why* for the next redesign.

## TL;DR

Blueprint 5.0 makes three cuts, one merge, and one addition.

**Cuts.** `/refactor`, `/review`, `/test-conventions` and their private
agents (`test-runner`, `conventions-evaluator`) are deleted. So is
`commit-writer`; `/commit` writes the message inline.

**Merge.** `spec-evaluator` and `design-evaluator` collapse into one
`evaluator` agent. It takes a file path and a methodology reference and
returns findings plus a verdict. It **does not edit** — the same
"assesses, never edits" rule the referee already follows.

**Addition.** A single **produce → judge → revise** loop, bounded at
three rounds, applied uniformly to the three things blueprint produces or
gates: the design doc, the spec, and the implementation. Each round
dispatches a *fresh* judge; the producer revises the whole artifact
against the judge's findings. The human reviews once, at loop exit,
instead of once per round.

The pipeline becomes:

```
/design ⟲ ──→ /spec ⟲ ──→ ⟦ implement ⟲ /verify ⟧ ──→ /commit
```

We are trading the evaluator's ability to fix things itself, and three
standalone utilities, for a smaller surface and a loop that produces
coherent artifacts. That trade is the whole argument.

## The problem

Three months of daily use on 4.0 show three things.

**1. The used surface is a third of the shipped surface.** In practice
every session is `/blueprint` plus an external `/loop` that keeps
re-running implement-then-verify until the verdict is clean enough for a
human to read. `/refactor`, `/review`, `/test-conventions` are never
invoked. They cost 504 lines of skill text, 195 lines of agent text, and
a share of every `/blueprint` invocation's workflow map. The plugin
carries 3,392 lines across 24 files; the path actually exercised runs
through roughly half of them.

**2. Specs come out incoherent.** 4.0 specs regularly contain sections
that contradict each other, sentences that don't say what they mean, and
ordering that makes the reader scroll back and forth. The root cause is
structural, not a prompt tweak. `spec-evaluator` runs a "fix loop" in
**one context**: it reads the spec, edits a sentence here and adds a
scenario there, then re-reads its own edits. Two things go wrong at once.
The fresh-context property the agent was created for is gone after the
first `Edit`. And nobody owns whole-document coherence — the evaluator
patches locally, the writer never sees the patched result, and the seams
show. `references/review-spec.md` Phase 4 does look for "two sections
that imply different behavior," but it has no lens for terminology
drift, ordering, or plain readability, and neither do the seven phases in
`review-design.md`.

**3. The loop that works is not part of the tool.** The referee verdict
*does* pay off on complex tasks: on the most recent run it found a blind
spot the implementer had missed, and the second pass was materially
better. But that loop is driven by hand, with a human gate after every
round. The human's real job is the final review; the per-round gates are
ceremony. (The FeatureBench N=5 run in `plugins/blueprint/README.md`
could not separate the referee round from a plain second pass. That
result stands and is not relitigated here; the decision to build the loop
in rests on direct use on harder tasks than FeatureBench's.)

`commit-writer` is a smaller version of problem 1: a second agent spun up
to read a diff the main session already has in front of it, for a
message whose quality nothing measures.

## Constraints shaping the solution

- **Agent-agnostic stays.** 4.0's identity is that blueprint produces
  intent and referees output; it does not drive the implementation. Any
  loop we add must preserve that: the loop body hands a punch list to
  *whoever* is implementing, and this session is merely the default
  implementer.
- **Judgment stays fresh-context.** The referee's value rests on not
  having written the code. The same holds for document judgment.
- **The eval harness keeps working.** `evals/blueprint-featurebench/`
  invokes the `spec` and `verify` skills by name, headless, and already
  runs a mechanized verify→repair round (Arm C) whose handoff is
  "previous patch + referee verdict + redo instruction" in
  `prompts/repair_instruction.md`. The built-in loop reuses that shape
  rather than inventing a second one.
- **One person maintains this.** Every extra file is a file that drifts
  the next time a model or a convention changes.

## Proposed approach

### The loop primitive

One protocol, written once in `references/loop.md`, read by `/design`,
`/spec`, and `/blueprint`:

```
ledger = []                      # owned by the calling skill, not the judge
round  = 1
loop:
  producer  → artifact (whole thing, not a patch)
  judge     ← artifact + ledger's open items
  judge     → each open item marked resolved | still open, plus new findings, plus verdict
  ledger    ← judge's report            (fresh subagent each round, report-only)
  if verdict is READY                   → exit: present to human
  if round == 3                         → exit: present ledger + artifact
  if nothing resolved and nothing new   → exit: present as stuck
  producer  ← ledger; round += 1
```

The **ledger** is the cross-round state. The calling skill (the session
running `/design`, `/spec`, or `/blueprint`) holds it; the judge never
sees a prior judge's context, only the list of open items it is asked to
re-check. That is the one concession to fresh-context purity: the judge
is told what to look at again, not what to conclude. "Stuck" is defined
on the ledger — a round that resolves nothing and finds nothing new —
which stays well-defined even though two fresh judges never phrase the
same finding identically. The same ledger feeds the referee; passing
prior open items in the dispatch prompt needs no change to `referee.md`.

Three instantiations:

| Stage | Producer | Judge | READY means |
|---|---|---|---|
| `/design` | this session, writing | `evaluator` + `review-design.md` | argument strength High, no human-input items |
| `/spec` | this session, writing | `evaluator` + `review-spec.md` | testability High, no human-input items |
| implement | any coding agent (default: this session) | `referee` | spec's Definition of Done met |

The revise step is a **whole-artifact rewrite** by the producer. For
documents that means the writer, holding the full intent, regenerates the
file with the findings in hand. For code it means the implementing agent
gets the ledger in the Arm C handoff *shape* — prior verdict plus a redo
instruction — and produces the next version **on the working tree**, not
from a pristine checkout. Arm C restarts from pristine because it is
measuring feedback quality; the built-in loop is repairing, and the
hand-driven loop that motivated it worked on the tree. The message
format is shared; the reset policy is not. Nobody patches someone else's
work in a context that has lost its freshness.

Human gates move to loop exits: approve the design, approve the spec,
review the verdict. Inside a loop there is no gate.

### One evaluator, report-only

`spec-evaluator` and `design-evaluator` are the same 70-line skeleton
with a different `references/review-*.md` plugged in: fresh-context
framing, locate file, apply phases, sort findings into "fix myself" versus
"ask the human," emit three sections. The methodology already lives in
the references. The merged `evaluator` agent:

- **Input:** artifact path, methodology reference path.
- **Tools:** `Read`, `Glob`, `Grep`. No `Edit`.
- **Output:** findings grouped by phase (each with location and the
  concrete fix the producer should make), items needing human judgment,
  and a verdict (`READY` / `REVISE` / `NEEDS-HUMAN`).

Skills dispatch it by explicit `subagent_type`, so the merge carries no
triggering risk. `/review` was the report-only twin of these two agents;
it is subsumed, not lost.

### A coherence phase in both methodologies

`review-spec.md` and `review-design.md` each gain a phase that reads the
document as a document: one term per concept throughout, scenario IDs
that match the Definition of Done, sections ordered for a first-time
reader, one claim per sentence, no section that restates another. This
is the lens problem 2 was missing. It is a rubric for the writer's
rewrite as much as a check for the judge.

### What is deleted

| Removed | Why it can go |
|---|---|
| `/refactor` + `test-runner` | Never used. Any coding agent refactors on its own; the referee gates the result. |
| `/review` | Subsumed by the report-only `evaluator`. |
| `/test-conventions` + `conventions-evaluator` | Never used. The referee keeps its optional read of `docs/testing/test-conventions.md` for repos that have one. |
| `commit-writer` | `/commit` already carries the inline procedure as a fallback; it becomes the procedure. One rule replaces the agent: write from the diff, not from the conversation. |
| `references/review-test.md`, `eval-methodology.md` | `review-test.md` is read only by `/review`; `eval-methodology.md` is read by nothing. `review-impl.md` stays: the referee reads it. |

After 5.0 the plugin is one command, four skills (`design`, `spec`,
`verify`, `commit`), two agents (`evaluator`, `referee`), and the
references those actually read.

## Alternatives considered

**Keep the fix-loop evaluators and just add a coherence phase.** Cheapest
change. It does not fix the mechanism: the evaluator still edits in its
own context and the writer still never re-reads the whole document. A
coherence phase inside a local-patch loop finds the seams and then
creates new ones.

**Keep the external `/loop`.** Status quo. It works, but the loop's
stop condition lives in the human's head, every round pauses for a gate,
and the handoff between rounds is whatever the human pastes. Building it
in gives the loop a stated stop rule and the Arm C handoff shape, and
makes standalone `/spec` self-polishing rather than one-shot.

**One loop per stage, written in each skill.** Three copies of the
protocol drift independently. The primitive is short enough to live in
one reference; the per-stage table is the only thing that differs.

**Let the evaluator keep `Edit` but rewrite the whole file.** Keeps the
fix-it-yourself convenience. But the evaluator holds a critique, not the
intent; a full rewrite by the critic is the surest way to lose what the
author meant. Judgment and generation stay separate — the referee
already made that call for code.

**Keep `commit-writer` on a cheap model.** It is already on `sonnet`.
The cost is not the tokens, it is the extra agent definition and the
dispatch round-trip for a task the main session can do in one turn.

## Trade-offs we are accepting

**Whole-artifact rewrites cost more than patches.** Each document round
regenerates a few hundred to a couple thousand words. Bounded at three
rounds, that is trivial next to the cost of an implementation built on
a contradictory spec.

**Losing `/refactor` and `/test-conventions` as capabilities.** Both are
real ideas. Neither earned use in three months, and both can be
resurrected from git history if that changes. Shipping unused surface
has a maintenance cost today; the option value is preserved at zero
cost.

**A step back toward driving.** When this session is the implementer,
`/blueprint` running implement→verify rounds looks like the 3.x driver.
The difference is what the loop body contains: a punch list and "produce
the next version," not a procedure. The implementing agent's internal
loop is still its own. This is the line, and it is stated so it can be
held.

**Judge noise across rounds.** Fresh judges may raise different findings
on the same artifact. The ledger makes convergence checkable; it does
not prevent oscillation, where round 3 re-opens what round 2 marked
resolved. Round cap plus human review at exit is the backstop.

## Riskiest assumptions

**That a whole-artifact rewrite against a ledger converges in three
rounds without regressing what earlier rounds fixed.** If writers
routinely reintroduce round-1 problems while fixing round-2 findings, the
loop produces churn and the human reviews a moving target. Mitigation is
in the protocol: the producer receives the ledger, each item marked
resolved or open, not just the latest round's findings. If that is not
enough, the fallback is the rejected alternative — evaluator keeps
`Edit` for mechanical fixes only (hedge words, missing header) and the
rewrite handles the rest.

**That a judged round beats a plain redo.** The loop's payoff rests on
the judge adding signal the producer would not find by re-reading its
own work. Direct use on complex tasks says yes; the N=5 FeatureBench
run could not tell the two apart. The Arm C rerun in Follow-ups is the
stated test. If it comes back null at larger N, the loop stays — it
still removes the per-round human gates — but the judge stage for
documents should be reconsidered against a cheaper self-review pass.

## How we'll know it worked

| Signal | Baseline (4.0) | Target (5.0) |
|---|---|---|
| Plugin size | 24 files, 3,392 lines | ≤ 16 files, ≤ 2,200 lines |
| External `/loop` needed for a `/blueprint` run | every session | none |
| `evaluator` **contradiction** findings on round 2 | not measured; observed on most specs | 0 on the next five specs written with 5.0 |
| FeatureBench Arm C and the built-in loop share a handoff format | separate prompt | one `repair_instruction.md` shape, differing only in reset policy |

Plugin size counts prompt-carrying files (command, skills, agents,
references); `README.md`, `CHANGELOG.md`, and `plugin.json` are excluded.

The spec row is the one that matters: it is the observed failure that
motivated the redesign, and it is checkable by reading the round-2
ledger of the next five specs. It is deliberately narrowed to
contradictions; a coherence phase will find *some* wording or ordering
nit on almost any document, so "zero findings" would be unreachable by
construction.

## Out of scope

- Referee changes. Steps 4–5 trimming and model tier are open questions
  the FeatureBench harness can answer later; `referee.md` is untouched.
- Real mutation tooling behind the anti-vacuity check.
- Multi-agent implementation (parallel implementers, agent selection).
- Any change to spec or design doc *templates* beyond the coherence
  rubric.

## Follow-ups

- Rerun FeatureBench Arm C with the built-in loop to check the handoff
  shape and whether three judged rounds beat three plain redos at the
  same cost ceiling. This is the test of the second riskiest assumption.

# 2609.0002 Loop Findings Never Narrow Scope; Ledger Persists

**Date:** 2026-09-10
**Status:** abandoned — see 2609.0003
**Author:** EP Lin
**Design doc:** [2609.0001](../../docs/designs/2609.0001_blueprint_5_slim_loop_evaluator.md) (this is an amendment, not a new design)

## Context

The clean paired rerun (`evals/blueprint-featurebench/reports/2609_clean_paired_astropy_n5/`)
showed the 5.0 `/spec` loop cutting hidden-test pass rate from 0.84 (4.0
spec) to 0.37, below no-spec. The mechanism is scope narrowing: the
evaluator's scope-discipline phases fence the spec to the literal problem
statement, the implementing agent honours the fence ("outside my stated
scope … left untouched"), and the neighbouring definitions the task also
needs never get restored. The 4.0 `vo` spec instead listed every stripped
neighbour in the touched file as an in-scope prerequisite.

Separately, the harness never captured the evaluator's ledger, so the
design's own success metric — contradiction findings per round — has no
data.

## Motivation

A judge that trims the producer's scope makes the producer build less.
The loop exists to make the artifact more coherent and more complete
against its goal, and to route genuine product-behaviour decisions to a
human. Everything else it finds should be included by default, not fenced
off.

## Proposed Solution

### Overview

Every finding a judge raises has one of three kinds. Two are resolved by
the producer autonomously; one goes to the human. The judge never
proposes removing goal-related work, and an "out of scope" entry is only
valid when it records a product-behaviour decision a human declined. The
loop keeps revising while any autonomous kind is open and exits with
questions when no autonomous row is open and at least one human-kind row
is. The
ledger is written to disk as a sibling of the artifact, one table per
round, and stage 01 of the FeatureBench harness copies it and records its
counts.

### Interface Contract

**Finding kinds** — a new `Kind` column in every ledger row. The
discriminator between the two scope kinds is **whether the goal already
determines the answer**, not whether the product's surface changes:

| Kind | Meaning | Who resolves |
|---|---|---|
| `contradiction` | two parts of the artifact disagree, or a term drifts | producer, autonomously |
| `uncovered` | goal-related scope the artifact does not cover — a prerequisite, a neighbour the feature's code path or tests reach, an edge the goal implies — and the goal, the code path, and the existing tests together determine what the behaviour must be, leaving the producer no choice to make | producer, autonomously: **add** it, marked `[INFERRED]` |
| `behavior-change` | resolving it requires a choice the goal leaves open — including whether to change behaviour that currently works and the goal did not mention — or it is an item a methodology's "Flag for human" line names: anything only the human can decide | human, via Needs human input |

One test, applied twice: **is a choice required?** Restoring something
that is absent is not a choice; altering something that already works is.
Worked example, from the finding that motivates this spec: definitions
stripped from `astropy/io/votable/tree.py` that the feature's code path
and tests reach are `uncovered` — they are absent, and the goal, the code
path, and the tests determine what they must be. Deciding whether the
parser should *also* reject a malformed attribute the goal never
mentions, or rewriting a working function's return type, is
`behavior-change`.

The `behavior-change` kind also carries the human routing 5.0 already
had: the "Flag for human" items in `references/review-design.md`
Phases 1–5 (straw-man alternative, no downside named, no load-bearing
assumption, qualitative success metric, design-invalidating open
question) are `behavior-change` rows. The name is a poor fit for them —
see Open Questions — but the routing is unchanged and no flag is lost.

**Ledger row**:

```markdown
| ID | Kind | Phase | Finding | Location | Fix | Status |
```

**`behavior-change` rows and questions are one set.** Every open
`behavior-change` row has exactly one matching question under the judge's
**Needs human input**, and nothing else appears there. "No human-input
items" and "no open `behavior-change` rows" are therefore the same
condition, not two counts.

**Stop rules** (replaces the 5.0 order), applied in this order:

1. `READY` → exit. Requires all three: no open rows of any kind, no
   human-input items, and the methodology's passing summary value
   (testability High / argument strength High).
2. Round cap 3 → exit, presenting the ledger, the artifact, and any open
   `behavior-change` rows as questions.
3. Stuck (a round that resolves zero rows and adds zero rows) → exit,
   presenting the same three things as the round cap does.
4. `NEEDS-HUMAN` → exit with the questions, when no `contradiction` and
   no `uncovered` row is open and at least one `behavior-change` row is
   open. (With zero open rows of any kind and no questions, rule 1 or
   rule 5 applies instead — never this one.)
5. `REVISE` → next round, in every other case: any open `contradiction`
   or `uncovered` row, including when `behavior-change` rows are open
   alongside them; and the case of zero open rows with a summary value
   below its passing threshold.

**Scope rule**, stated once in `references/loop.md` and applied by every
methodology: a judge may add scope and may never remove goal-related
scope. An "Out of Scope" / "do not restore" / "leave as-is" entry is
valid only when it names a `behavior-change` decision a human declined;
any other such entry is itself a `contradiction` finding with
`Fix: remove the fence and cover it`.

**Two markers, two authors.** `[ASSUMPTION: …]` stays what it is in
`skills/design/SKILL.md`: something the *writer* guessed. `[INFERRED]`
marks scope a *judge* raised as `uncovered` and the producer added. They
are not synonyms and neither replaces the other.

**Implement loop.** The referee has no Needs-human-input section and
`commands/blueprint.md` forbids a human gate between rounds, so
`NEEDS-HUMAN` cannot fire there: the implement loop's stop rules are
rules 1, 2, 3, and 5 above, with rule 4 stated as not applicable. Its
rows carry a `Kind` derived by the calling skill (see Open Questions).

**Ledger file** — written by the producing skill at every judge round,
as a sibling of the artifact with `.ledger.md` replacing `.md`:

```
.blueprint/specs/{id}_{name}.ledger.md
docs/designs/{id}_{topic}.ledger.md
```

Content: one `## Ledger — round {n}` table per round, appended in
order, then an `## Exit` line naming the stop rule that fired. Each
table is the **merged ledger snapshot after that round** — every row
raised so far, `open` or `resolved`, as `loop.md`'s format block already
shows — not the judge's update in isolation. A later
loop over the same artifact (the implement loop over a spec) appends its
own round sections and its own `## Exit` after the existing ones; round
numbering restarts at 1 for each loop, so `## Ledger — round` headings —
not the highest round number — are what a reader counts.

**Ledger siblings must never be mistaken for artifacts.** Any
"most-recently-modified `.md`" discovery over `.blueprint/specs/` or
`docs/designs/` excludes `*.ledger.md`; the ledger is always newer than
the artifact it belongs to. This applies to `agents/evaluator.md`'s
artifact-location fallback and to the harness's `newest_spec_file`.

**Harness** (`evals/blueprint-featurebench/scripts/01_make_specs.py`):
after resolving the spec path, look for the sibling ledger (the spec
path with `.md` replaced by `.ledger.md`); copy it to
`results/specs/{id}.ledger.md`; add to `.meta.json`:

- `ledger_found: bool`
- `ledger_rounds: int` — the count of `## Ledger — round` headings
- `ledger_path` — the copied file's path relative to the harness root (present only when found)
- `ledger_rows` — a **list, one entry per round in file order**, each
  entry a `{kind: {open: n, resolved: n}}` map whose keys are all three
  kinds always, zero-filled when a kind has no rows in that round,
  plus an `unclassified` integer for rows whose `Kind` is not one of the
  three or whose `Status` does not start with `open`/`resolved` (or the
  synonyms `fixed`, `addressed`, `done`, `closed`, `unresolved`,
  `pending`). Status is classified by its first word so a producer that
  writes "resolved (round 2 rewrite)" still counts; anything else is
  surfaced, never silently dropped.
  Because each table is a cumulative snapshot, `resolved` is cumulative
  and per-round new findings are the IDs first appearing in that round's
  table. A list rather than a final-round map, because the metric the
  design claims is contradiction findings *per round*.

A ledger that is absent is recorded (`ledger_found: false`,
`ledger_rounds: 0`, `ledger_rows: []`) and the task is still `ok`. A
ledger that is present but has no parseable round table is recorded the
same way except `ledger_found: true`; it is never a task failure.
`prompts/spec_headless.md` rule 3 permits the ledger sibling.

No other harness stage needs a change: every other consumer of
`results/specs/` addresses `{id}.md` and `{id}.meta.json` by exact name
rather than globbing.

## Alternatives Considered

### Revert `/spec` to 4.0's single in-place evaluator pass

The only measured arm that scored well (0.84 pass rate). Not chosen: the
4.0 evaluator edited the spec inside its own context, which is the
mechanism behind the contradictory specs 5.0 was built to remove, and the
rerun did not measure spec coherence at all — so the 0.84 says the 4.0
spec was a broader briefing, not a better document. The revert would trade
an unmeasured regression for a measured one. The three-kind taxonomy keeps
the fresh-judge loop and removes the one behaviour (fencing) the rerun
pinned as the cause; the vo probe is the test of whether that is enough.

### A fourth kind for the design methodology's "Flag for human" items

Would name straw-man alternatives and missing assumptions honestly
instead of stretching `behavior-change`. Not chosen: routing is identical
(human, via Needs human input), so a fourth kind adds a column value and
no behaviour. Recorded under Open Questions in case the stretch confuses
judges in practice.

- **S2:** Given `references/loop.md`, when reading it, then it states the scope rule in substance: a judge may add scope and never removes goal-related scope; an out-of-scope entry is valid only for a `behavior-change` decision a human declined; any other such entry is a `contradiction` finding whose fix is to remove the fence.
- **S3:** Given `references/loop.md`, when reading its stop rules — both the prose list and the `## Protocol` pseudocode block, which state the same order — then the five rules of the Interface Contract appear in that order, `NEEDS-HUMAN` is conditioned on "no open `contradiction` or `uncovered` row and at least one open `behavior-change` row", the round-cap and stuck exits present open `behavior-change` rows as questions, and the ledger table header and its example rows include a `Kind` column.
- **S4:** Given `references/loop.md`, when reading it, then it names the ledger file path convention (`.ledger.md` sibling, for both `.blueprint/specs/` and `docs/designs/`), one table per round appended in order, the `## Exit` line naming the stop rule that fired, and the rule that artifact discovery excludes `*.ledger.md`.

### Evaluator

## Trade-offs and Limitations

- Inclusion by default will sometimes add work a human would have
  declined; the `[INFERRED]` marker plus the gate is the correction path.
- `behavior-change` vs `uncovered` is the judge's call; a judge that
  labels a behaviour change `uncovered` slips it past the human. The
  marker makes it visible at the gate.
- Design docs lose the autonomous scope-creep trim; a bloated design now
  reaches the human with `uncovered` items listed rather than pre-cut.

## Open Questions

None of these blocks implementation: ship the proposed default, and a
later answer changes prose, not scenarios.

- [ ] **Is `behavior-change` the right name now that it also carries the
  design methodology's straw-man, missing-downside, and
  missing-assumption flags?** A straw-man alternative is not a behaviour
  change. Proposed default: keep the name, accept the stretch, since a
  fourth kind would buy nothing the routing does not already do.
- [ ] **What `Kind` does a referee punch-list row carry?** The referee's
  three item types (uncovered scenario, covered-but-vacuous scenario,
  quality blocker) do not map onto `contradiction` / `uncovered` /
  `behavior-change`. Proposed default, pending a decision: uncovered and
  vacuous scenarios → `uncovered`; quality blockers → `contradiction`;
  the implement loop never produces `behavior-change`. S11 does not
  depend on the answer — it only requires that a `Kind` is set.
- [ ] **Should the implement loop append to the spec's `.ledger.md` at
  all?** The spec loop already wrote that file. Proposed default:
  append its rounds and its own `## Exit` after the existing sections.
  The alternative is a separate `.implement.ledger.md`, which keeps each
  loop's rounds trivially separable at the cost of a second convention.

# 2609.0001 Blueprint 5.0 — Slim Plugin, One Loop, One Evaluator

**Date:** 2026-09-10
**Status:** abandoned — see 2609.0003
**Author:** EP Lin
**Design doc:** [2609.0001](../../docs/designs/2609.0001_blueprint_5_slim_loop_evaluator.md)

## Context

The blueprint plugin at `plugins/blueprint/` is 4.0.0: one command
(`commands/blueprint.md`), seven skills, six agents, ten references. The
design doc records three months of use: only the `/blueprint → /spec →
implement → /verify → /commit` path is exercised, the spec and design
evaluators edit documents in their own context and produce incoherent
specs, and the implement↔verify loop that pays off on hard tasks is
driven by hand with an external `/loop`.

The plugin is prose, not code. There is no test runner; every scenario
below is checked by file existence, frontmatter fields, and content
grep, exactly as the 4.0 spec was.

## Motivation

Shipping unused surface costs maintenance on every model or convention
change. Incoherent specs cost an implementation round. A hand-driven loop
costs a human gate per round when the human's real job is one review at
the end. All three are fixed by the same 5.0 change set.

## Proposed Solution

### Overview

Delete three skills, four agents, and two references. Merge the two
document evaluators into one report-only `evaluator` agent. Add one loop
protocol in `references/loop.md` that `/design`, `/spec`, and
`/blueprint` follow: produce → fresh judge → whole-artifact revise,
bounded at three rounds, with a ledger carrying findings across rounds.
Move human gates to loop exits. `/commit` writes inline. `referee.md` is
untouched.

### Key Components

- **`references/loop.md`** — the loop protocol: round cap, ledger
  format, the three stop rules, the working-tree reset policy, and the
  handoff prompt shape shared with the FeatureBench Arm C repair
  instruction.
- **`agents/evaluator.md`** — the single document judge. Takes an
  artifact path, a methodology reference path, and an optional ledger of
  open items. Returns a ledger update and a verdict. Has no `Edit`.
- **`references/review-spec.md`, `references/review-design.md`** — each
  gains a coherence phase.
- **`skills/design/SKILL.md`, `skills/spec/SKILL.md`** — run the loop
  from `loop.md` with `evaluator` as judge; the skill's own session is
  the producer and rewrites the whole document each round.
- **`commands/blueprint.md`** — chains `/design ⟲ ──→ /spec ⟲ ──→
  ⟦ implement ⟲ /verify ⟧ ──→ /commit`, runs the implement loop with
  `referee` as judge, gates only at loop exits.
- **`skills/verify/SKILL.md`** — unchanged in what it checks; accepts an
  optional ledger to forward to the referee so `/blueprint` can reuse it
  per round. Standalone invocation is one round.
- **`skills/commit/SKILL.md`** — the inline procedure becomes the
  procedure; no agent dispatch.

### Data Flow

1. Producer writes the whole artifact (document to disk, or code on the
   working tree).
2. Calling skill dispatches a fresh judge with the artifact location, the
   methodology (for documents), and the ledger's open items.
3. Judge returns: each open item marked `resolved` or `open`, new
   findings, human-input items, and a verdict.
4. Calling skill merges the report into the ledger and applies the stop
   rules: `READY` → present to human; `NEEDS-HUMAN` → present the
   questions to the human; round 3 → present ledger and artifact;
   nothing resolved and nothing new → present as stuck.
5. Otherwise (verdict `REVISE`) the producer receives the full ledger and
   rewrites; round increments.

### Interface Contract

**Ledger** — markdown the calling skill maintains and passes verbatim:

```markdown
## Ledger — round {n}

| ID | Phase | Finding | Location | Fix | Status |
|----|-------|---------|----------|-----|--------|
| F1 | Testability | "handles errors gracefully" is untestable | §Proposed Solution ¶3 | state the status code and body | open |
| F2 | Coherence | "referee" and "verifier" used for the same agent | §Overview, §Data Flow | pick one term | resolved |
```

`Status` is `open` or `resolved`. IDs are stable across rounds; a judge
never renumbers.

**Judge dispatch prompt** (documents):

```
Artifact: {path}
Methodology: {reference path}
Ledger open items: {table rows with Status=open, or "none"}
```

**Judge report** — three sections, in order:

```markdown
### Ledger update
{every open item re-stated with Status resolved|open, then new rows}

### Needs human input
{questions only; "none" if empty}

### Verdict
READY | REVISE | NEEDS-HUMAN
```

`READY` requires all three: no open rows, no human-input items, and the
methodology's own summary at its passing value — testability High for
`review-spec.md`, argument strength High for `review-design.md`.
`NEEDS-HUMAN` means at least one human-input item exists regardless of
rows. `REVISE` otherwise.

**Implement-round dispatch prompt** (to the `referee`, which is
unchanged and therefore instructed in the prompt, not in `referee.md`):

```
Spec: {path}
Base git ref: {ref, or "none"}
Ledger open items: {table rows with Status=open, or "none"}
For each open item above, state in your report whether the condition it
describes is still present.
```

The calling skill — not the referee — owns the implement ledger: it
derives one row per referee punch-list item (uncovered scenario,
covered-but-vacuous scenario, quality blocker), sets `Phase` to the
referee check that raised it, and marks a row `resolved` when the next
round's report no longer lists that item. Implement `READY` is the
referee's `Meets the spec's Definition of Done: Yes`.

**Implement-round handoff** (to the implementing agent), same shape as
`evals/blueprint-featurebench/prompts/repair_instruction.md` minus that
prompt's previous-patch block and its pristine-repository instruction:

```
## Previous round
{referee verdict, verbatim}
{ledger}

## Instruction
Produce the next version on the current working tree, addressing every
open item. Do not revert to a clean checkout.
```

**Stop rules** (fixed values), applied in this order: verdict `READY` →
exit, present to human; verdict `NEEDS-HUMAN` → exit, present the
questions to the human; round cap 3 → exit, present ledger and artifact;
stuck (a round whose ledger update resolves zero items and adds zero
rows) → exit, present as stuck. Only `REVISE` continues the loop.

**Breaking changes:** `/refactor`, `/review`, `/test-conventions`,
`spec-evaluator`, `design-evaluator`, `conventions-evaluator`,
`test-runner`, `commit-writer` no longer exist. Any external prompt that
dispatches them by name breaks. The FeatureBench harness dispatches
only the `spec` and `verify` skills and is unaffected.

## Alternatives Considered

Argued in the design doc: keep fix-loop evaluators plus a coherence
phase; keep the external `/loop`; one loop per skill; evaluator keeps
`Edit` for whole-file rewrites; keep `commit-writer` on a cheap model.
Not repeated here.

## For the Implementing Agent

> **Your job:** make every acceptance scenario above hold. This is a
> prose plugin: there is no test suite, so "tests" here are the file
> existence, frontmatter, and grep checks each scenario names. Every
> scenario must be checkable by someone who has only this spec and the
> tree — cite the exact file and the exact string a checker would grep.

Implement however you work best. Only the result is checked. Specific
guidance for this change:

- Write `references/loop.md` first; `commands/blueprint.md`,
  `skills/design/SKILL.md`, and `skills/spec/SKILL.md` refer to it rather
  than restating it. One protocol, one file.
- The `evaluator` agent is the 4.0 `spec-evaluator` skeleton with the
  fix-loop removed and the methodology path parameterised. Keep the
  fresh-context framing and the "never soften requirements / never invent
  business rules" principles.
- Do not touch `agents/referee.md`. If a change there looks necessary,
  it belongs in a follow-up; pass ledger context in the dispatch prompt.
- Do not modify anything under `evals/`.
- Skill descriptions must stay pushy: the trigger phrases in the 4.0
  `description` fields are load-bearing for skill activation and should
  survive the rewrite.

## Trade-offs and Limitations

- Deleting `/refactor` and `/test-conventions` removes real capabilities
  that never earned use; they remain recoverable from git history.
- The ledger passes prior open items to a fresh judge, which is a small
  concession to fresh-context purity, accepted so "stuck" is definable.
- The loop is bounded, not convergent; oscillation across rounds is
  caught by the round cap and the human review at exit, not prevented.
- The referee is untouched, so the implement loop's ledger semantics
  live entirely in the dispatch prompt and `loop.md`.

## Open Questions

- [ ] Post-ship, not a blocker: `model` for `evaluator` ships as `opus`
  (S6), inherited from the 4.0 evaluators. Whether it can drop to
  `sonnet` now that it no longer edits is a question for the FeatureBench
  rerun, not for this implementation.
- [ ] Post-ship, not a blocker: `NEEDS-HUMAN` exits the loop (Interface
  Contract stop rules). The alternative — carry human-input items forward
  and keep revising until the rows clear — was not chosen because it makes
  `READY` unreachable whenever a question is open, and so burns the round
  cap on every such run.

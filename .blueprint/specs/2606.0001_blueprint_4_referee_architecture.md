# 2606.0001 Blueprint 4.0 — Intent Producer + Referee

**Date:** 2026-06-04
**Status:** accepted
**Author:** EP Lin

**Design doc:** [2606.0001](../../docs/designs/2606.0001_blueprint_4_referee_architecture.md)

## Context

Blueprint is a Claude Code plugin (at `plugins/blueprint/`) implementing a
full-cycle TDD workflow: `/design → /spec → /plan → /run → /refactor →
/commit`, with fresh-context evaluator subagents after each stage. Its back
half (`/plan` → `/run`) is a heavily choreographed TDD executor: parse a
slice DAG, walk slices in dependency order, batch-write tests, dispatch a
batch evaluator, verify all-fail, commit the failing batch, implement, run a
bounded ≤5 fix loop, then an autonomous refactor pass, then a verifier.

The approved design doc argues for deleting that machine. Blueprint 4.0
re-architects the plugin from a prescriptive TDD **driver** into an intent
**producer** + **referee**: it produces a human-facing design doc and an
agent-executable spec contract, hands implementation to any coding agent,
and referees the output with fresh-context evaluators. See the design doc
for the full argument and the authoritative "what lives / dies / transforms"
table; this spec turns that table and the new pipeline into a verifiable
acceptance contract.

## Motivation

Two structural problems get worse over time in the current architecture:
most of `/run`'s choreography is model-compensation for 2024–25 weaknesses
that decays into overhead as models improve, and the maintenance entropy is
concentrated almost entirely in that back half. Separately, "let any coding
agent implement this" is a protocol problem — procedure (slice order, batch
cadence, fix-loop count) binds one specific agent, while intent (design +
spec + test-quality principles) is portable. The redesign sheds the
high-entropy, agent-specific half and keeps the durable, portable half.

The one thing that must not be lost is TDD's **anti-vacuity guarantee** — a
test fails when the behavior it covers is wrong. Procedure is dropped;
the guarantee is re-secured post-hoc by the `/verify` referee.

## Proposed Solution

### Overview

Collapse the pipeline to `/design → /spec → ⟦any coding agent implements⟧
→ /verify → /commit`, with `/refactor · /review` as standalone
utilities. Delete the driver machine (`/run`, `/plan`, and their
run-internal evaluators) and the `/proto` spike command. Transform `run-evaluator` into an agent-agnostic
referee behind a new `/verify` skill. Elevate `/spec` so its output is the
executable contract handed to the implementing agent. Relocate the
test-quality references so they serve both as generator guidance (bundled
into the spec) and as the referee's enforced rubric.

The implementation is prompt/skill engineering — editing, deleting, and
adding Markdown skill/agent/reference files plus `plugin.json`. There is no
runtime test suite; every acceptance scenario below is a concrete,
checkable fact about the resulting plugin files and their content.

### Key Components

- **`/verify` skill** (`plugins/blueprint/skills/verify/SKILL.md`, new) —
  the referee. Dispatches a fresh-context referee subagent that, on
  whatever any agent produced, runs four checks: (1) spec-scenario coverage
  matrix, (2) lightweight thought-mutation anti-vacuity check, (3) Test
  Desiderata scoring, (4) implementation-quality flags. Treats its input as
  adversarial / unknown-provenance.
- **Referee subagent** (transformed from `agents/run-evaluator.md` into a
  new file under `agents/`, e.g. `agents/referee.md` or
  `agents/verify-evaluator.md`; the exact name is implementer's choice as
  long as it is not `run-evaluator` and the name `/verify` dispatches
  resolves to it) — agent-agnostic; no longer coupled to `/run` and no
  longer named `run-evaluator`. The old `agents/run-evaluator.md` path no
  longer exists.
- **Elevated `/spec`** (`skills/spec/SKILL.md`, + surviving
  `agents/spec-evaluator.md`) — its output template gains the
  agent-executable contract elements (interface contract inherited from
  design, explicit implementing-agent instruction, bundled test-quality
  principles, a Definition of Done worded as exactly what `/verify` checks).
- **Relocated references** — `references/test-desiderata.md` and
  `references/anti-patterns.md` are cited by both `/spec` (generator
  guidance) and `/verify` (referee rubric).
- **Deleted machine** — `skills/run/`, `skills/plan/`,
  `agents/plan-evaluator.md`, `agents/test-batch-evaluator.md`,
  `agents/refactor-runner.md`, the references that served only the
  deleted machinery (`references/review-plan.md`,
  `references/review-test-batch.md`), and the `/proto` spike command
  (`commands/proto.md`) — a prescribed procedure, the kind 4.0 sheds.
- **Surviving utilities** — `/design` (+ `design-evaluator`), `/refactor`
  (+ `test-runner`), `/commit` (+ `commit-writer`), `/review`,
  and the `/blueprint` orchestrator (rewritten to chain the new pipeline).

### Data Flow

The new workflow a user walks:

1. `/design` produces a human-facing decision doc (when the approach is in
   question; skippable).
2. `/spec` produces the agent-executable contract from the design (or
   directly).
3. Any coding agent implements against the contract — blueprint does not
   drive this step.
4. `/verify` referees the produced code + tests against the spec.
5. `/commit` writes the message.

### API / Interface Changes

The plugin's "API" is its set of slash commands and the documented
pipeline. Changes:

```
Removed commands/skills:  /run, /plan, /proto
New skill:                /verify
Renamed orchestrator:     /tdd → /blueprint  (rewritten to chain /design → /spec → ⟦agent⟧ → /verify → /commit)
Unchanged utilities:      /design, /spec, /refactor, /commit, /review
plugin.json:              version → 4.0.0; description → "intent producer + referee"
```

## Acceptance Scenarios

Each scenario is verifiable by inspecting the resulting plugin files. "Removed"
means the path does not exist; "documents" / "references" means the named
string/concept is present (or absent) in the file's content.

### Deletions — the driver machine is gone
- **S1:** Given the 4.0 plugin, when inspecting `plugins/blueprint/skills/`, then `run/` and `plan/` directories do not exist.
- **S2:** Given the 4.0 plugin, when inspecting `plugins/blueprint/agents/`, then `plan-evaluator.md`, `test-batch-evaluator.md`, and `refactor-runner.md` do not exist, and `run-evaluator.md` does not exist either (it was renamed when transformed into the referee — see S6).
- **S3:** Given the 4.0 plugin, when inspecting `plugins/blueprint/references/`, then `review-plan.md` and `review-test-batch.md` do not exist (they served only the deleted machinery).
- **S4:** Given the whole `plugins/blueprint/` tree with `CHANGELOG.md` excluded from the search set, when grepping every remaining file for the deleted-machinery names `/run`, `/plan`, "slice DAG", "test-batch-evaluator", "refactor-runner", or "run-evaluator", then there are zero matches outside the `references/eval-methodology.md` historical study artifact (see S4a). In particular: no live skill or command file (notably `commands/blueprint.md`) retains a "What's new in v3.x" recap block or any other prose describing the deleted machine as part of the live workflow. (`CHANGELOG.md` is the sole home for version history of these terms.)
- **S4a:** Given the surviving reference files that the referee and `/spec` still cite — `references/review-impl.md` and `references/review-spec.md` — when reading them, then any guidance that assumes a `/run` slice loop or a plan file (per-slice completion status, failing-test-commit checkpoints, slice-referential examples, "Ready for /plan" verdict) is either removed or rewritten to be agent-agnostic and pipeline-current, so the rubric the referee enforces matches the 4.0 pipeline. **Pinned surgery for `review-impl.md`:** strip the slice/run-loop phases (the per-slice completion-status and failing-test-commit phases) and retain the implementation-quality flagging content (stale docstrings, restated-*what* comments, task-referential rot, dead/commented-out code) as the referee's check 4, reframed for code of unknown provenance. (`references/eval-methodology.md` is an empirical-study record of the 3.x experiment; its historical mentions of slice batching may remain as dated study context and are out of scope for rewriting.)

### Transform — the `/verify` referee exists and is agent-agnostic
- **S5:** Given the 4.0 plugin, when inspecting `plugins/blueprint/skills/`, then `verify/SKILL.md` exists, its frontmatter `name` is `verify`, and its `description` contains explicit trigger language for refereeing/verifying produced code against a spec (e.g., phrases such as "verify", "referee", "check the implementation against the spec", "scenario coverage") so the skill fires on those requests.
- **S6:** Given the referee subagent file (the renamed transform of the old `agents/run-evaluator.md`, now under `agents/` with a non-`run-evaluator` name that `/verify` dispatches), when reading it, then its `name` frontmatter is not `run-evaluator`, it contains no dependency on a plan graph or `/run` having executed (no reference to `*_graph.md`, slices, or "after the /run skill finishes"), and it explicitly frames its input as adversarial / unknown-provenance ("treat as code of unknown origin", not "our own careful output").
- **S7:** Given the `/verify` skill (and its referee subagent), when reading the methodology, then all four checks are present and named: (1) spec-scenario coverage matrix, (2) thought-mutation anti-vacuity check, (3) Test Desiderata scoring, (4) implementation-quality flags.
- **S8:** Given the `/verify` anti-vacuity check, when reading its instructions, then it directs the referee to ask, per covered behavior, "what is the smallest change to the implementation that breaks this behavior, and would any existing test catch it?" and to flag covered-but-vacuous scenarios.
- **S9:** Given the `/verify` skill, when reading its inputs, then it consumes the spec's acceptance scenarios as the coverage baseline and does not require a plan file.

### Elevate — `/spec` output is the executable contract
- **S10:** Given the elevated `/spec` skill, when reading its output template, then the template requires an "interface contract" section inherited from the design doc (API shapes, error taxonomy, breaking-change rules).
- **S11:** Given the elevated `/spec` template, when reading it, then it requires an explicit instruction addressed to the implementing agent: "make every scenario pass with tests that would fail if the behavior were wrong."
- **S12:** Given the elevated `/spec` template, when reading it, then it bundles (inline or by reference) the test-quality principles from `references/test-desiderata.md` and `references/anti-patterns.md` as generator guidance.
- **S13:** Given the elevated `/spec` template, when reading it, then it requires a "Definition of Done" section worded as exactly the checks `/verify` performs, so the contract and the rubric are the same list read from two ends.
- **S14:** Given the elevated `/spec` skill, when reading its "Next Step", then it points to the implementing-agent handoff and then `/verify` — not to `/plan` (which no longer exists).

### Keep — utilities survive, repositioned outside the core pipeline
- **S15:** Given the 4.0 plugin, when inspecting skills and agents, then `/design` (+ `design-evaluator`), `/spec` (+ `spec-evaluator`), `/refactor` (+ `test-runner`), `/commit` (+ `commit-writer`), and `/review` all still exist. (`/review` at `skills/review/SKILL.md`; the rest under `skills/` with their paired agents under `agents/`.)
- **S16:** Given the surviving utilities (`/refactor` and `/review`), when reading their framing in README and `commands/blueprint.md`, then they are documented as standalone utilities available any time, not as core-pipeline stages.

### Relocate — references serve a dual role
- **S17:** Given the 4.0 plugin, when inspecting `references/`, then `test-desiderata.md` and `anti-patterns.md` still exist and are cited by both `/spec` (as generator guidance) and `/verify` (as the referee rubric).

### Pipeline documentation is consistent everywhere
- **S18:** Given `plugins/blueprint/README.md`, when reading it, then the documented pipeline is `/design → /spec → ⟦any coding agent implements⟧ → /verify → /commit`, the framing is "intent producer + invariant referee" (not "TDD-pure executor"), and the tests-as-contract philosophy is retained and described as strengthened.
- **S18a:** Given `plugins/blueprint/README.md`, when reading the artifact-definition prose, the Skills table, and the Comparison table, then they describe `/spec` as the agent-executable contract (not "build-time scaffolding that drives `/plan` and `/run`"), contain no `/plan` or `/run` rows in the Skills table, add a `/verify` row, and contain no surviving description of the deleted plan/execution-graph artifact as a live workflow stage (any `plan` mention is historical, not a current pipeline step).
- **S19:** Given `plugins/blueprint/commands/blueprint.md`, when reading the orchestrator, then it chains `/design → /spec → ⟦agent⟧ → /verify → /commit` with human gates, and contains no `/plan` or `/run` step.
- **S20:** Given the 4.0 plugin, when inspecting `plugins/blueprint/commands/`, then only `blueprint.md` exists — `tdd.md` does not exist (the orchestrator was renamed `/tdd` → `/blueprint`), and `proto.md` and `migrate-paths.md` do not exist (the `/proto` spike command and the vestigial v3.6 `/migrate-paths` aid are both removed). No surviving file references `/tdd` or `/proto` as a live command.
- **S21:** Given `plugins/blueprint/CHANGELOG.md`, when reading the top entry, then a `4.0.0` entry documents the breaking change: the driver machine removed, `/verify` added, `/spec` elevated, and the migration note ("finish in 3.x or restart in 4.0").
- **S22:** Given `plugins/blueprint/.claude-plugin/plugin.json`, when reading it, then `version` is `4.0.0` and the `description` reflects "intent producer + referee" while preserving tests-as-contract.
- **S22a:** Given the repo-root `.claude-plugin/marketplace.json`, when reading the `blueprint` plugin entry, then its `description` no longer describes the deleted driver model ("implementation plans", "parallelizable work streams", "execution graphs") and is consistent with the 4.0 "intent producer + referee" framing.

### Self-consistency of the build
- **S23:** Given the full 4.0 plugin, when listing every skill, command, and agent referenced anywhere in README, `commands/blueprint.md`, and the repo-root `.claude-plugin/marketplace.json`, then (a) every referenced skill resolves to an existing `skills/<name>/SKILL.md`, every referenced command to an existing `commands/<name>.md`, and every dispatched agent to an existing `agents/<name>.md`; (b) no skill, command, or agent file is orphaned (referenced nowhere in the live tree, CHANGELOG excepted); and (c) no live reference resolves to a deleted/renamed target (`/run`, `/plan`, `/proto`, `plan-evaluator`, `test-batch-evaluator`, `refactor-runner`, `run-evaluator`).

## Trade-offs and Limitations

- **Weaker correctness guarantee than 3.x at launch.** The fail-first
  structural guarantee is replaced by referee thought-mutation reasoning,
  which depends on referee quality. Mitigated later by real mutation
  tooling (out of scope here).
- **Referee is a single point of failure.** Quality concentrates in
  `/verify` rather than many small gates.
- **No per-slice commit archaeology.** The implementing agent commits
  however it commits.

## Out of Scope

The following are explicitly **not** part of 4.0 (named as follow-ups in
the design doc):

- Real mutation-testing integration (mutmut / Stryker / PIT).
- Machine-readable spec serialization (JSON/YAML contract).
- Multi-agent / agent-colony orchestration.
- A 3.x → 4.0 automated migration tool (migration is "finish in 3.x or
  restart in 4.0").

## Definition of Done

The implementing agent is done when all acceptance scenarios hold —
S1–S23 including S4a, S18a, and S22a — and the design doc's "what lives /
dies / transforms" table is fully reflected in the plugin tree. Verify
with `/verify` against this spec once the `/verify` skill itself exists;
until then, every scenario is directly inspectable by file existence and
content grep.

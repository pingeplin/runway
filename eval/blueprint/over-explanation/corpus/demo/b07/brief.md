# Multi-tenant audit log

Design a tamper-evident, multi-tenant audit logging subsystem for our SaaS platform. The platform serves many independent customer organizations, called tenants, on shared infrastructure, and we need a trustworthy record of who did what and when. This is a design brief: the deliverable is a design document that specifies the data model, the invariants, and the public interfaces, not a working implementation.

The core requirement is that the audit log is append-only. Once an entry has been written, it can never be modified or deleted through any application path, and the design must make in-place edits and out-of-order insertion structurally impossible rather than merely discouraged by convention.

To make tampering evident, entries within a tenant are linked into a hash chain. Each entry stores the cryptographic hash of the immediately preceding entry for that tenant, so the entry carries a `prev_hash` field that is computed over the previous entry's canonical serialized content. The very first entry for a tenant chains from a fixed, well-known genesis value rather than from a real predecessor. Because each entry's own hash is derived from its content together with the `prev_hash` it carries, altering or removing any historical entry breaks the chain for every entry that follows it, and a verifier walking the chain from genesis can detect the break. The design must therefore include a chain-verification routine that recomputes hashes along a tenant's chain and reports the first position, if any, at which the stored hash and the recomputed hash disagree.

Per-tenant isolation is a hard requirement. Each tenant's entries form their own independent hash chain, and no entry from one tenant may ever appear in, or be readable through, another tenant's chain. Every read and every write must be scoped to exactly one tenant, identified by a `tenant_id` that is supplied by the caller and is never inferred from the entry payload. Cross-tenant queries are out of scope and are explicitly disallowed by this design.

Each audit entry records, at minimum, the acting principal (the `actor_id`), the action performed, the target resource, and the timestamp at which the action occurred. The log must be queryable by actor and by time range within a single tenant, so an operator investigating an incident can ask for every action a given actor took during a given window. Query results are returned in ascending timestamp order. Timestamps are stored as UTC and are assigned by the logging subsystem at write time, not taken from untrusted client input, so that ordering reflects server-observed time.

The subsystem exposes three public operations. The first, `append`, takes a `tenant_id` and an entry payload, links the new entry onto that tenant's chain, and returns the stored entry including its computed hash and chain position. The second, `query`, takes a `tenant_id` together with an optional actor filter and an optional inclusive time range, and returns the matching entries in ascending timestamp order. The third, `verify_chain`, takes a `tenant_id`, walks that tenant's chain from genesis, and returns the position of the first tampered entry, or a no-tampering result when the chain is intact.

Retention is policy-driven. Each tenant has a configured retention period, and entries older than that period are eligible for deletion by a scheduled retention job. Retention is the only path by which entries may leave the log, and it must delete only whole contiguous prefixes of a tenant's chain — that is, the oldest entries first — so that the surviving entries still form an unbroken chain from a new, recorded checkpoint. The retention job records the hash of the last deleted entry as the new chain anchor for that tenant, so that verification of the truncated chain remains possible after pruning.
